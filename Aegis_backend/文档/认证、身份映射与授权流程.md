# Aegis PA 认证、身份映射与授权流程

本文说明当前后端已经实现的认证、身份映射和数据授权机制，供后续开发受保护接口时参考。内容以现有代码为准。

## 1. 设计边界

Aegis 不保存用户密码，也不实现自己的账号密码登录接口。

- **Keycloak**：负责登录、签发 access token、保存签名私钥。
- **Vue 前端**：完成 OIDC 登录后获取 access token；每次调用 Aegis 受保护接口时，在 `Authorization` 请求头携带它。
- **Aegis 后端**：验证 token，映射到本地用户和租户，并以该身份执行后续业务操作。
- **PostgreSQL**：利用行级安全（RLS）限制租户范围数据。

推荐的正式前端登录方式为 OIDC 授权码模式加 PKCE。开发联调时可通过 Keycloak Token Endpoint 获取短期 access token；Direct Access Grant 仅限本地测试。

## 2. 核心身份标识

Token 不能直接等同于 Aegis 用户。系统使用两组标识完成外部认证到本地业务身份的转换：

```text
Keycloak 外部身份                    Aegis 本地业务身份
oidc_issuer + oidc_subject (sub)  →  users.id + users.tenant_id
```

`oidc_issuer + oidc_subject` 是外部身份的稳定唯一键：

- `oidc_issuer`：签发 token 的 OIDC Realm 地址，例如 `http://127.0.0.1:8080/realms/aegis`。
- `oidc_subject`：Token 的 `sub` 声明，即该 Realm 中用户的唯一 ID。
- `users.id`：Aegis 内部 `user_id`。
- `users.tenant_id`：用户所属组织的 `tenant_id`。

不能只使用 `sub` 映射用户。不同 OIDC 服务或不同 Realm 可能生成相同的 `sub`，而 `issuer + sub` 的组合可以区分它们。

## 3. 请求处理流程

所有使用 `get_current_user` 的接口遵循下列流程：

```text
前端携带 Authorization: Bearer <access_token>
                 ↓
FastAPI HTTPBearer 提取 token
                 ↓
OIDCAuthenticator 验证 JWT
  ├─ 通过 Discovery 获取 JWKS 公钥
  ├─ 使用 token header 的 kid 选择公钥
  ├─ 仅允许 RS256 签名
  ├─ 验证签名、exp、iat、iss、aud、sub
  └─ 校验 azp（存在时必须等于配置的前端 Client ID）
                 ↓
提取 issuer、sub、email、name / preferred_username
                 ↓
按 issuer + sub 查询 users 与 tenants
  ├─ 用户和租户均为 active：获得本地 user_id、tenant_id
  ├─ 开发自动映射开启：创建或复用本地映射
  └─ 否则：返回 403
                 ↓
在事务中 SET LOCAL app.tenant_id、app.user_id
                 ↓
执行具体业务接口，PostgreSQL RLS 再限制数据范围
```

当前已实现的 `POST /conversations` 即为第一个受保护接口。它的主要业务职责是创建会话；JWT 验证和本地身份映射是它与未来受保护接口共用的前置依赖。

## 4. Token 验证实现

实现文件：[app/security/auth_security.py](../app/security/auth_security.py)。

`OIDCAuthenticator` 的行为如下：

1. 使用 `OIDC_ISSUER_URL/.well-known/openid-configuration` 获取 OIDC Discovery 文档。
2. 严格比对 Discovery 返回的 `issuer` 是否与配置一致。
3. 读取 `jwks_uri`，下载 Keycloak 的公开 JWKS。
4. 通过 JWT header 中的 `kid` 选择对应公钥，以 RS256 验证签名。
5. JWKS 默认缓存 300 秒。找不到 `kid` 时会立刻刷新一次，兼容 Keycloak 密钥轮换。
6. 验证成功后才读取 claims；无 `sub` 或 `email` 的 token 会被拒绝。

后端不保存、也不需要 Keycloak 私钥。私钥只在 Keycloak 中用于签发 token；Aegis 使用 Keycloak 公布的公钥验证签名。

### 当前验证的 claims

| Claim | 验证或用途 |
| --- | --- |
| `exp` | 必须存在，PyJWT 验证未过期 |
| `iat` | 必须存在 |
| `iss` | 必须等于 `OIDC_ISSUER_URL` |
| `aud` | 必须包含 `OIDC_AUDIENCE` |
| `sub` | 必须存在，用于本地用户映射 |
| `email` | 必须存在，用于本地资料 |
| `azp` | 若存在，必须等于 `OIDC_CLIENT_ID` |
| `name` / `preferred_username` | 作为本地展示名，缺失时使用 email |

当前并不保存 access token、refresh token 或 id token。后端只在本次请求内验证和读取 access token。

## 5. 本地用户与租户映射

实现文件：

- [app/security/dependencies.py](../app/security/dependencies.py)
- [app/service/identity_service.py](../app/service/identity_service.py)
- [app/repository/user_repository.py](../app/repository/user_repository.py)

`get_current_user` 是 Controller 使用的认证依赖，返回 `CurrentUser`。它包含已经验证并映射完成的本地 `LocalUser`。

查询条件如下：

```sql
WHERE u.oidc_issuer = :issuer
  AND u.oidc_subject = :subject
  AND u.status = 'active'
  AND t.status = 'active'
```

因此，有效 Keycloak 账号不自动等于拥有 Aegis 访问权。用户记录不存在、用户被禁用或租户被禁用时，均不能继续执行业务操作。

### 开发环境自动映射

以下配置同时满足时，未知 OIDC 用户会自动创建或复用本地用户：

```env
AUTO_PROVISION_USERS=true
DEFAULT_TENANT_NAME=aegis-dev
```

自动映射仅适合本地开发。生产环境应保持：

```env
AUTO_PROVISION_USERS=false
```

并由管理员或未来的受控注册/邀请流程预先创建租户成员关系。

当前 Jason 的最小开发映射可由以下脚本手动写入：

- [scripts/seed_current_keycloak_user.sql](../scripts/seed_current_keycloak_user.sql)

脚本仅创建 `aegis-dev` 租户及与当前 Keycloak Jason 用户匹配的 `users` 记录；不包含 token、密码或真实第三方凭据。

## 6. 授权和数据库 RLS

实现文件：[app/config/database.py](../app/config/database.py)。

认证成功并获得 `LocalUser` 后，`get_tenant_session` 会调用 `tenant_transaction`：

```sql
SELECT
  set_config('app.tenant_id', :tenant_id, true),
  set_config('app.user_id', :user_id, true);
```

第三个参数为 `true`，等价于在当前事务中使用 `SET LOCAL`；事务结束后该上下文自动失效。Python 的 `ContextVar` 也会在依赖结束后复位，防止请求之间串用身份。

数据库 RLS 策略会以当前事务中的 `app.tenant_id`、`app.user_id` 为条件。以 `conversations` 为例，用户只能读写自己的会话：

```sql
tenant_id = aegis_current_tenant_id()
AND user_id = aegis_current_user_id()
```

当前启用 RLS 的表包括会话、第三方连接、邮件快照、邮件草稿、已发送邮件、待办草稿、确认项、长期记忆等。业务代码也必须始终使用 `get_tenant_session`，不能在 Controller 中自行创建未设置租户上下文的会话。

## 7. HTTP 状态码与排查

| 状态码 | 含义 | 常见原因 |
| --- | --- | --- |
| `401 Unauthorized` | token 未通过认证 | 缺少 Bearer header、token 过期、签名无效、Issuer/Audience/AZP 不匹配、JWKS 不可达 |
| `403 Forbidden` | token 有效，但没有本地 Aegis 成员资格 | `users` 中不存在对应 `issuer + sub`，或用户/租户状态非 active |
| `201 Created` | 已通过认证、授权并成功创建会话 | `POST /conversations` 成功 |
| `500 Internal Server Error` | 基础设施或未处理的服务端错误 | 例如 PostgreSQL 用户名/密码、数据库连接或权限配置错误 |

排查时只记录 `sub`、请求 ID 等必要信息，绝不能在日志、聊天、截图或 Git 中记录完整 access token、refresh token、数据库密码或模型密钥。

## 8. 后续接口接入模板

新建受保护 Controller 接口时，应复用以下两个依赖：

```python
from fastapi import Depends
from sqlalchemy.ext.asyncio import AsyncSession

from app.security.dependencies import CurrentUser, get_current_user, get_tenant_session


async def protected_endpoint(
    current_user: CurrentUser = Depends(get_current_user),
    session: AsyncSession = Depends(get_tenant_session),
) -> dict:
    # 仅使用 current_user.user.id 和 current_user.user.tenant_id 作为数据归属。
    # 不接受前端传来的 user_id、tenant_id 作为权限依据。
    ...
```

创建、查询和更新租户范围数据时：

- 从 `current_user.user` 获取 `user_id`、`tenant_id`；
- 不信任客户端传来的租户或用户标识；
- 使用 `session` 进行数据库访问，以确保 RLS 上下文存在；
- 对跨用户、管理员和多租户成员等将来场景，增加明确的角色/成员关系模型和权限策略，不要绕过 RLS。
