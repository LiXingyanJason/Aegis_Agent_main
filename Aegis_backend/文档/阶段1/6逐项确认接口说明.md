# 逐项确认接口说明

本接口用于用户对会议草稿等外部写入操作逐项作出“批准”或“拒绝”。接口先保存决定；只有数据库事务提交成功后，才通过 Redis 投递恢复消息，使 Agent Worker 以相同 `run_id` 恢复 LangGraph。会议创建分支会在恢复后再次核验批准记录，才调用日历工具。

## 提交决定

`POST /approvals/{approval_item_id}/decision`

请求需携带已登录用户的 Bearer access token。只能操作当前用户、当前租户内的确认项。

请求体：

```json
{
  "decision": "approved"
}
```

或：

```json
{
  "decision": "rejected",
  "reason": "这个时间不合适"
}
```

成功响应：

```json
{
  "data": {
    "approval_item_id": "uuid",
    "run_id": "uuid",
    "decision": "approved",
    "approval_status": "approved_executing",
    "execution_scheduled": true
  }
}
```

## 当前状态规则

| 用户决定 | `approval_items.status` | 是否创建日历 |
| --- | --- | --- |
| `approved` | `approved_executing` → `executed` / `failed` | 是；恢复 LangGraph 后调用 `calendar.create_event`，成功时才创建。 |
| `rejected` | `rejected` | 否；提交后恢复 LangGraph，生成拒绝结果。 |
| 已过期 | `expired` | 否。 |

接口会锁定 `approval_items` 行，只有状态为 `pending` 且未过期的项目可被决定一次。重复确认、已拒绝、已执行或已过期的项目均返回 `409 Conflict`；不存在或不属于当前用户的项目返回 `404`。

## 恢复链路

`POST /approvals/{approval_item_id}/decision` 在当前租户事务内锁定确认项、写入 `approval_decisions` 并更新 `approval_items`。事务提交后才向 Redis 投递 `{run_id, resume_decision}`；Worker 二次核验该任务确有相同的已保存决定，随后以 `thread_id = run_id` 从 PostgreSQL Checkpoint 恢复 LangGraph。

`execution_scheduled=true` 表示批准决定已成功登记恢复任务，不代表第三方日历已经创建成功。恢复后的写入节点会再次验证批准状态、使用绑定的幂等键调用 `calendar.create_event`，并将确认项更新为 `executed` 或 `failed`。
