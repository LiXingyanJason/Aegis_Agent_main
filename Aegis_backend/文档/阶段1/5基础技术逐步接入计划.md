# 基础技术逐步接入计划

本文记录 Aegis PA 在当前“对话任务 + Redis Worker + SSE + Calendar MCP 只读查询”基础上，逐步接入 Alembic、OpenTelemetry、MCP Python SDK 和 LangGraph 的实施路线。

本轮不处理跨服务联邦认证、真实 Google/Outlook OAuth、Prometheus/Grafana/Loki、Celery、pgvector 和 Kubernetes。

## 1. 接入顺序

实际执行顺序为：

```text
Alembic
    ↓
最小 OpenTelemetry + JSON 结构化日志
    ↓
MCP Python SDK + Calendar MCP Tool Registry
    ↓
LangGraph：日历草稿—确认—恢复写入
```

尽管 LangGraph 在候选技术中排在 MCP SDK 前，Calendar MCP 即将新增写入工具。先标准化 MCP 工具承载方式，再实现等待确认后恢复的写入工作流，可减少返工。

## 2. 阶段 0：冻结现有基线

### 目标

确认基础设施接入前的可用版本，避免无法区分新问题与既有问题。

### 工作项

- 保留现有 SQL 初始化脚本作为当前数据库结构依据；
- 记录 PostgreSQL 实际 schema、RLS 策略和开发种子数据；
- 验证对话、Redis Worker、SSE、LLM、Calendar MCP 的只读链路；
- 执行现有后端与 Calendar MCP Server 测试。

### 验收标准

```text
前端任务 → Agent Worker → Calendar MCP → SSE 工具预览 → Agent 回复
```

在引入新技术前能够稳定完成。

## 3. 阶段 1：接入 Alembic

**实施状态：已完成（2026-10-05）。**

### 目标

将手动执行 SQL 脚本升级为受版本控制的数据库迁移。日历草稿、确认项、外部事件结果以及邮件功能后续产生的表结构变更，均必须经迁移发布。

### 工作项

1. 在 `Aegis_backend` 中加入 `alembic` 依赖。
2. 创建基础结构：

```text
alembic.ini
migrations/
├── env.py
├── script.py.mako
└── versions/
```

3. `env.py` 使用项目已有数据库配置，并兼容 PostgreSQL、异步 SQLAlchemy 与 RLS 租户上下文。
4. 根据现有脚本建立迁移版本：

```text
001_baseline_schema
002_msg_client_id_uq
```

5. 新数据库使用：

```powershell
alembic upgrade head
```

6. 已按旧脚本初始化的开发数据库，先核对结构后使用：

```powershell
alembic stamp 002_msg_client_id_uq
```

`stamp` 仅登记当前版本，不会重复创建已有表。

7. 后续日历写入能力通过新增迁移实现，例如：

```text
003_add_calendar_drafts_and_approval_items
004_add_calendar_external_event_result
```

### 验收标准

- 空数据库可通过 `alembic upgrade head` 初始化；
- 已有开发库可安全纳入迁移版本管理；
- 既有会话、SSE 和 Calendar MCP 只读功能正常；
- 后续业务结构变更不再新增手工建表 SQL。

## 4. 阶段 2：接入最小 OpenTelemetry 与结构化日志

**实施状态：已完成（2026-10-05）。**

### 目标

让一次任务能够跨 API、Redis、Worker、LLM 和 Calendar MCP 进行定位与追踪。

一期不立即部署 Prometheus、Grafana、Loki 或 Alertmanager；先建立 Trace、关联标识和 JSON 日志基础。

### 工作项

1. 为任务链路统一关联以下标识：

```text
request_id
trace_id
conversation_id
run_id
step_id
tool_call_id
```

2. 为关键调用创建 Span：

```text
HTTP POST /conversations/{conversation_id}/messages
    └─ dispatch_agent_run
        └─ agent.execute
            ├─ calendar.list_events / calendar.find_free_time
            │   └─ HTTP POST Calendar MCP /mcp
            └─ llm.complete
```

3. 优先接入 FastAPI、HTTPX、SQLAlchemy、Redis 入队、Redis Worker 消费和 Agent 编排步骤。
4. 修改 Redis 队列载荷，由单一字符串 `run_id` 扩展为：

```json
{
  "run_id": "...",
  "traceparent": "..."
}
```

Worker 消费任务后恢复 Trace 上下文。

5. 逐步将 Worker 中的 `print()` 改为 JSON 结构化日志，至少输出：

```json
{
  "event": "tool_call_completed",
  "run_id": "...",
  "tool_call_id": "...",
  "tool_name": "calendar.list_events",
  "duration_ms": 420,
  "status": "succeeded"
}
```

### 本次实现

- 新增 `app/observability/`：集中管理 Trace 初始化、JSON 日志格式及 Redis 队列的 Trace Context 编解码；
- FastAPI、HTTPX、SQLAlchemy、Redis 自动埋点已在 API 与 Worker 进程启动时启用；
- HTTP 请求的 W3C `traceparent` 随 Redis 队列消息写入，Worker 在消费后恢复父上下文并创建 `agent.consume` Span；旧版仅含 `run_id` 的队列消息仍可消费；
- 新建 `agent_runs` 时保留既有 `request_id`，并将当前 Trace 的 `trace_id` 写入现有 `agent_runs.trace_id` 字段，便于从数据库任务记录回溯日志；
- Agent 对 `llm.complete` 与 `tool.invoke` 创建业务 Span；HTTPX 自动记录模型服务与 Calendar MCP 的出站请求；
- Worker 启动、任务接收、完成、异常，以及工具成功/失败均输出 JSON 日志。日志字段限定为 `run_id`、`tool_call_id`、工具名、状态、错误码、耗时等，不记录 token、API Key、提示词、邮件正文或第三方凭据；
- 默认仅生成 Trace Context 与日志中的 `trace_id`。本地要在控制台查看完整 Span 时，在 `.env` 设置 `OTEL_CONSOLE_EXPORTER=true` 后重启 API 和 Worker。

### 验收标准

- 可通过 `run_id` 查询 API、Worker、LLM、MCP 的完整日志；
- Calendar MCP 调用失败时可定位请求、工具、错误码与耗时；
- access token、API Key、邮件正文、第三方凭据不会写入 Trace 或日志。

## 5. 阶段 3：接入 MCP Python SDK 与工具注册表

**实施状态：已完成（2026-10-05）。**

### 目标

保持 Aegis 主后端现有 Tool Gateway 契约不变，将 Calendar MCP Server 的协议承载升级为标准 MCP SDK，并避免 MCPService 随工具增加而堆积 `if/elif`。

### 工作项

1. 在 `Calendar_mcp_server` 内部增加 MCP 工具注册表和 Handler：

```text
app/tool/
├── contracts.py
├── registry.py
├── list_events_handler.py
└── find_free_time_handler.py
```

2. 调整职责：

```text
MCPService
    处理已由 SDK 解析的 tools/call 业务上下文
        ↓
MCPToolRegistry
    根据工具名找到 ToolHandler
        ↓
具体 ToolHandler
    调用 CalendarService
```

3. 引入并固定 MCP Python SDK 版本。
4. Calendar MCP Server 使用 SDK 暴露标准工具；`CalendarMCPClient` 改为通过 SDK Client Session 调用。
5. 保持以下主后端对象稳定，避免业务层依赖 SDK：

```text
ToolDefinition
ToolInvocation
ToolContext
ToolResult
ToolError
ToolGateway
```

6. 增加协议兼容测试，覆盖：

- `initialize`；
- `tools/list`；
- `calendar.list_events`；
- `calendar.find_free_time`；
- 无效工具名、无效时间参数、无效 Aegis `_meta`；
- 服务 API Key 不匹配。

### 本次实现

- 两个项目均固定依赖 `mcp==2.3.0`；
- Calendar MCP Server 使用 MCP SDK 2.x 的 `MCPServer` 暴露标准 Streamable HTTP 服务。SDK 接管 `initialize`、`tools/list`、`tools/call` 及会话/协议处理；
- 新增 `Calendar_mcp_server/app/tool/` 下的 `CalendarToolHandler` 契约、`MCPToolRegistry`、`ListEventsHandler`、`FindFreeTimeHandler`；新增工具时不再修改 `MCPService` 的工具名分支；
- `MCPService` 只负责把 SDK 提供的 `_meta` 解析为受控 Aegis 上下文，并委托 Registry 调用 Handler；
- 主后端 `CalendarMCPClient` 使用 SDK `streamable_http_client + ClientSession`，并向前者注入 `httpx2.AsyncClient` 管理鉴权头与超时；通过 `call_tool(..., meta=...)` 传递 Aegis 上下文；主后端自己的 Tool Gateway 契约保持不变；
- 服务端保留 Bearer API Key 校验，并新增 MCP 协议兼容测试，覆盖初始化、工具发现、两个只读工具、无效工具/时间/_meta 及 API Key 不匹配。

### 验收标准

- 日历工具新增时不需要修改 `MCPService` 的具体工具名分支；
- Aegis 前端和 Tool Gateway 接口无需改变；
- 既有只读日历工具兼容；
- MCP Client 与 Server 使用兼容的 SDK 版本；
- 工具调用仍保留 `run_id`、`tool_call_id` 等审计关联。

## 6. 阶段 4：接入 LangGraph，完成日历确认工作流

### 目标

完成一期 3.2 的“查找时间—生成草稿—用户确认—创建日历事件”闭环。

不要一次性将全部 Agent 重写为 LangGraph。本阶段只将日历写入工作流作为第一条 Graph 链路接入。

### 状态图

```text
load_context
    ↓
route_calendar_intent
    ↓
query_availability
    ↓
create_calendar_draft
    ↓
create_approval_item
    ↓
interrupt：等待用户确认
    ├─ rejected → completed_rejected
    └─ approved
          ↓
      calendar.create_event
          ↓
      persist_external_event_result
          ↓
      completed
```

### 工作项

1. 新增日历草稿、确认项、外部事件结果相关 Alembic 迁移。
2. 将 Graph 的 `thread_id` 固定为 `run_id`。
3. 业务事实仍保存于 PostgreSQL：

```text
agent_runs
run_steps
calendar_drafts
approval_items
tool_calls
run_events
```

LangGraph 仅保存流程恢复所需 checkpoint，不替代业务表。

4. 用户批准确认项时：

```text
验证 approval_item、参数哈希与幂等键
    ↓
恢复 run_id 对应的 LangGraph checkpoint
    ↓
调用 calendar.create_event
    ↓
保存 external_event_id 与执行结果
    ↓
发布 SSE completed / failed 事件
```

5. 新增 `calendar.create_event` MCP 工具，风险等级为 `write`。
6. 该工具调用前必须验证：

```text
存在 calendar_draft
存在 approval_item
approval 状态为 approved
参数哈希一致
幂等键有效
```

### 验收标准

- 用户可查询空闲时间并生成站内会议草稿；
- 未批准时绝不调用 `calendar.create_event`；
- 批准一次最多创建一个外部日历事件；
- 重复批准或网络重试不会重复创建会议；
- SSE 可展示等待确认、写入执行、完成或失败状态；
- Mock Provider 返回外部事件 ID，后续可替换为真实 Provider。
