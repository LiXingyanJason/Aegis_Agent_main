# 第02期总体开发计划与接口设计（持续维护）

> 文档状态：**规划稿，非已实现接口清单**。本文作为阶段二后续工作的总入口，记录范围、优先级、依赖、专题设计和验收；已上线接口仍以实际代码及根目录《第01期-接口设计.md》为准。本文中标记“待规划”或“计划”的内容不能被前端当作可用能力。

## 1. 文档定位与维护规则

第01期文档描述现有接口及其补充；本文件承接后续阶段的整体规划，不以“日历改造”为文档主标题。每个专题在自己的小节内写清目标、操作、接口契约、前后端依赖及验收，不另设需要来回跳转的附录。新增专题时沿用这一结构，避免把某个功能的设计误读为整个阶段的全部工作。

状态统一使用“待规划 → 已设计 → 开发中 → 已实现 → 已验收”。只有代码、测试和接口文档同步后才能标记“已实现”；尚未确定的业务范围、日期和交付顺序不预先承诺。跨专题变更应同时更新影响范围、兼容策略和验收项。

## 2. 专题计划

### 2.1 日历页面会议创建、修改与取消

> 状态：**已设计，尚未实现**。本节扩展根目录《第01期-接口设计.md》3.2“日程查询与会议安排”及“日历展示页接口”。现有日历页面仍只有五个只读 GET 接口；Calendar MCP 目前支持 `calendar.list_events`、`calendar.get_event`、`calendar.find_free_time`、`calendar.create_event`，**尚无修改或取消工具**。不得因本节出现新路径就在前端显示可用按钮或模拟写入成功。

#### 2.1.1 目标与边界

日历页应能发起新建会议、修改本人有权管理的正式会议、取消本人有权管理的正式会议。所有外部写入均走“站内操作草稿 → 冻结预览 → 逐项确认 → 后端执行 → 重新查询正式日程”，不提供浏览器直连 Calendar MCP、无确认的 `POST/PATCH/DELETE /calendar/events`，也不把站内草稿当作已占用的正式日程。

- **新建**：页面提供“新建会议”入口；既有对话式安排会议与 `approval_required` 流程保持不变。新增的手动表单入口使用下文操作草稿接口，不调用 LLM，也不绕过逐项确认。
- **修改**：第一阶段仅允许修改 **Aegis 创建、当前用户拥有组织者/写入权限、非全天且非循环** 的正式会议。可改主题、描述、地点、起止时间及参会人；这些更改可能触发提供商通知，确认页必须展示差异。
- **取消**：界面称“取消会议”，不是删除站内记录。仅对上述可管理的正式会议开放；确认页提示可能向参会人发送取消通知。历史执行与审批审计保留。
- 其他用户或外部系统创建的事件、只读连接、循环系列及全天事件继续只读。未来扩大范围须补充提供商能力、版本与通知语义，不以 `origin_draft_id` 的缺失推断拥有权。

#### 2.1.2 现有能力与实施前置

| 能力 | 当前状态 | 阶段二要求 |
| --- | --- | --- |
| 日历来源、正式事件、事件详情、站内会议草稿查询 | 已实现，只读 | 保持响应兼容；详情增加可选能力字段 |
| 对话生成会议草稿、`approval_required`、逐项批准/拒绝 | 已实现 | 继续使用，不重复创建第二个会话任务 |
| `calendar.create_event` | 仅审批后由 Worker 调用 | 手动新建也必须经独立审批和幂等执行 |
| `calendar.update_event`、`calendar.cancel_event` | 未实现 | Calendar MCP、Provider Adapter、Worker 白名单及审计一起实现 |
| 提供商事件版本/条件写入 | 未实现 | 修改/取消必须有可校验版本；无能力时禁用操作 |

新增操作草稿不是现有 `calendar_event_drafts` 的无条件复用。需要独立的 `calendar_event_operation_drafts`（或等价、可审计的数据模型），保存动作、目标事件标识、基线版本、目标字段、草稿版本与生命周期。提交时创建或绑定可恢复的 `calendar_operation` 任务/Checkpoint、审批项及外部动作执行记录；不能在一个没有可恢复任务的页面请求中直接伪造现有审批项。具体表结构、迁移号、任务策略与工具预算在实现计划中定稿，本文不宣称已有迁移。

#### 2.1.3 页面操作与对应接口

| 页面操作 | 接口 | 外部副作用 |
| --- | --- | --- |
| 打开日历/切换月周日/点击正式事件 | 复用现有 `GET /calendar/calendars`、`GET /calendar/events`、`GET /calendar/events/detail` | 无 |
| 点击“新建会议”并保存表单 | `POST /calendar/operation-drafts`，`action=create` | 只保存站内草稿 |
| 点击“编辑会议”或“取消会议” | 先 `GET /calendar/events/detail`，再 `POST /calendar/operation-drafts`，`action=update/cancel` | 只保存站内草稿 |
| 继续编辑未提交草稿 | `GET /calendar/operation-drafts/{draft_id}`、`PATCH /calendar/operation-drafts/{draft_id}` | 只修改站内草稿 |
| 提交逐项确认 | `POST /calendar/operation-drafts/{draft_id}/submit` | 冻结版本并登记审批，不写提供商 |
| 批准或拒绝 | 复用 `GET /approvals/{approval_item_id}`、`POST /approvals/{approval_item_id}/decision` | 批准仅登记恢复；Worker 随后执行 |
| 查看最终结果 | 复用 `GET /runs/{run_id}`、SSE，之后重新查询正式日程及草稿 | 无新的页面写入 |

页面仅在服务端明确返回 `can_edit=true` 或 `can_cancel=true` 时显示对应按钮。“新建会议”还需有效 `calendar.write` 连接；`GET /calendar/calendars` 的 `can_create_with_approval` 只说明连接可能具备写权限，**不代表某次动作已批准**。按钮应在读取或执行失败时给出真实错误，不显示虚假成功。所有接口沿用 Bearer access token、统一 `{"data": ...}` 成功包装及当前用户/租户身份；浏览器不得提交 `tenant_id`、`user_id`、MCP 凭据或内部批准令牌。

#### 2.1.5 操作草稿接口（均为新增，未实现）

##### 2.1.5.1 创建草稿

`POST /calendar/operation-drafts`

公共请求字段：`action`（`create|update|cancel`）、`connection_id`、`calendar_id`（本期仅 `primary`）、`timezone`（IANA）、`client_request_id`（UUID，用于避免重复点击创建多个站内草稿）。`extra=forbid`。服务端从认证身份取得用户与租户，不接受前端指定 Provider 工具名、审批状态或幂等执行键。

`create` 示例：

```json
{
  "action": "create",
  "connection_id": "10000000-0000-4000-8000-000000000020",
  "calendar_id": "primary",
  "timezone": "Asia/Shanghai",
  "client_request_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "proposed_event": {
    "title": "项目同步",
    "start_at": "2026-10-26T09:00:00+08:00",
    "end_at": "2026-10-26T10:00:00+08:00",
    "description": "议题说明",
    "location": null,
    "attendees": ["lili@example.com"]
  }
}
```

`update` 必须同时传 `target`（`external_event_id`、`event_version`）和完整 `proposed_event`；不接受只传部分字段却默默清空参会人、描述或地点。`cancel` 只传 `target`、可选 `reason`，不得传 `proposed_event`。目标连接、日历和事件标识共同定位正式事件；从页面详情取得的版本必须与服务端再次读取的当前版本一致。服务端保存**事件原始快照与目标快照**，确认页展示逐字段差异。提交参会人邮箱仅来自用户编辑的表单，不自动从邮件正文或发件人补入。

`update` 请求示例（`proposed_event` 必须完整提交）：

```json
{
  "action": "update",
  "connection_id": "10000000-0000-4000-8000-000000000020",
  "calendar_id": "primary",
  "timezone": "Asia/Shanghai",
  "client_request_id": "bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb",
  "target": {"external_event_id": "mock-event-example", "event_version": "opaque-provider-revision"},
  "proposed_event": {
    "title": "项目复盘",
    "start_at": "2026-10-26T10:00:00+08:00",
    "end_at": "2026-10-26T11:00:00+08:00",
    "description": "议题说明",
    "location": null,
    "attendees": ["lili@example.com"]
  }
}
```

`cancel` 请求示例：

```json
{
  "action": "cancel",
  "connection_id": "10000000-0000-4000-8000-000000000020",
  "calendar_id": "primary",
  "timezone": "Asia/Shanghai",
  "client_request_id": "cccccccc-cccc-4ccc-8ccc-cccccccccccc",
  "target": {"external_event_id": "mock-event-example", "event_version": "opaque-provider-revision"},
  "reason": "会议不再需要"
}
```

校验：起止时间必须带显式 UTC 偏移、结束晚于开始；长度、时长上限、标题/描述/地点、邮箱格式和参会人数设定有界限制；不支持全天/循环事件。本期默认北京时间展示，但不得重新解释带偏移的 HTTP 时间。对新建/改期可先查询当前用户空闲作提示；空闲检查不证明其他参会人有空，也不是写入成功。连接、目标事件、权限及版本在草稿创建时核验，但**提交审批和最终执行仍须重新核验**。

成功 `201` 返回下述草稿详情，`status=draft`、`version=1`，不创建日历事件。

##### 2.1.5.2 读取与编辑站内草稿

- `GET /calendar/operation-drafts/{draft_id}`：只读返回本人草稿、原事件安全快照、目标快照、动作、状态、版本、关联 `run_id/approval_item_id`；不回传 Provider 凭据或原始邮件正文。
- `PATCH /calendar/operation-drafts/{draft_id}`：仅 `status=draft` 可操作；必须提交 `expected_version` 与完整可编辑字段，更新后版本递增。不可修改 `action`、目标事件标识、原事件快照或所属连接；需要改目标时重建草稿。已提交、已批准、拒绝或执行失败的草稿不能静默改写原审批预览。

例如更新新建/修改草稿时提交 `{"expected_version":1,"proposed_event":{...完整字段...}}`；取消草稿提交 `{"expected_version":1,"reason":"调整后的原因"}`。响应 `200` 返回更新后的草稿详情和新版本，前端必须使用新版本提交审批，不可继续发送旧版本。

草稿详情主要字段示例：

```json
{
  "data": {
    "draft_id": "33333333-3333-4333-8333-333333333333",
    "action": "update",
    "status": "draft",
    "version": 2,
    "connection_id": "10000000-0000-4000-8000-000000000020",
    "calendar_id": "primary",
    "target": {"external_event_id": "mock-event-example", "event_version": "opaque-provider-revision"},
    "original_event": {"title": "项目同步", "start_at": "2026-10-26T09:00:00+08:00", "end_at": "2026-10-26T10:00:00+08:00"},
    "proposed_event": {"title": "项目复盘", "start_at": "2026-10-26T10:00:00+08:00", "end_at": "2026-10-26T11:00:00+08:00", "description": "议题说明", "location": null, "attendees": ["lili@example.com"]},
    "run_id": null,
    "approval_item_id": null
  }
}
```

示例仅展示关键字段；正式 VO 还应包含创建/更新时间、确认过期时间等。`original_event` 在实际实现中应保存完整可比较字段，不允许用示例中的截断对象做差异判断。

##### 2.1.5.3 冻结并提交逐项确认

`POST /calendar/operation-drafts/{draft_id}/submit`

```json
{"expected_version": 2}
```

服务端短事务内锁定本人草稿，核验 `draft` 状态及版本、写入连接与目标、目标事件最新版本、时间约束和通知范围；冻结 `preview_snapshot` 与参数哈希，创建 `calendar_operation` 任务/Checkpoint 和**单独** `approval_item`。`resource_type=calendar_event_operation_draft`、`resource_id=draft_id`、`draft_version=2`；`action` 分别为 `calendar.create_event`、`calendar.update_event`、`calendar.cancel_event`，`risk_level=write`。审批预览必须列出原值与目标值、目标事件、参会人变动、提供商可能发送的邀请/更新/取消通知，以及“尚未执行”。取消会议需额外醒目提示，不得把取消预览写成删除历史记录。

成功 `202`：

```json
{
  "data": {
    "draft_id": "33333333-3333-4333-8333-333333333333",
    "version": 2,
    "status": "pending_approval",
    "run_id": "44444444-4444-4444-8444-444444444444",
    "approval_item_id": "55555555-5555-4555-8555-555555555555",
    "approval_status": "pending",
    "expires_at": "2026-10-26T01:20:00Z"
  }
}
```

重复提交相同草稿/版本应返回已创建的同一确认项，不得创建第二个运行或第二次外部动作。事务提交后才分发任务，任务停在等待确认点；发送既有 `approval_required` SSE，前端前往 `/confirmations?run_id=...`。未点击批准前，正式日程不得变化。

#### 2.1.6 批准、执行与结果

继续使用现有 `POST /approvals/{approval_item_id}/decision`：批准请求 `{"decision":"approved"}`，拒绝请求 `{"decision":"rejected","reason":"可选说明"}`。**现有后端参数没有 `checked` 字段**；是否已核对由用户在前端明确点击/勾选及服务端冻结版本保证，不能依赖旧文档示例中的 `checked:true`。批准响应 `execution_scheduled=true` 只表示已登记恢复，不能显示“会议已创建/已修改/已取消”。

Worker 恢复同一 `run_id` 后，先核验审批仍有效、冻结的草稿版本/参数哈希、当前连接及 `calendar.write`、资源归属、事件版本。随后通过受控 Calendar MCP 工具执行，并写 `external_action_executions` 幂等审计。修改/取消使用提供商的原子条件写入；若事件被其他端改变，标记稳定冲突并停止，不能覆盖新内容、自动重放或换目标事件。拒绝分支不调用外部写工具。失败或超时不得推断执行成功；不确定结果须按幂等键核验，不盲目重试。

任务可继续使用既有进度与终态 SSE；外部写成功后才发 `approval_executed`，并将站内草稿/审批项更新为 `executed`。前端收到成功事件或轮询确认后重新请求 `GET /calendar/events` 与 `GET /calendar/events/detail`，以提供商读取结果为准；取消后保留站内审计，但正式日历列表中不再显示该事件。若提供商仍返回事件或同步尚未完成，应展示“执行成功，正在刷新日历”，不可凭前端本地删除伪造完成状态。

现有对话式 `calendar.create_event` 草稿及审批恢复契约不变；手动表单草稿不得在同一次点击中既提交审批又自动批准。不得由邮件查询卡片、步骤事件、`calendar_decision` 或历史预览自动提交创建/修改/取消。

#### 2.1.7 错误、权限与前端状态

| 状态/错误码（建议） | 处理 |
| --- | --- |
| `401` | 登录失效，沿用 OIDC 处理 |
| `404 CALENDAR_EVENT_NOT_FOUND` / `DRAFT_NOT_FOUND` | 不存在或不属于本人统一返回；不暴露他人资源 |
| `409 CONNECTION_REQUIRED` | 缺少有效 `calendar.read`/`calendar.write`，提示连接；不展示模拟成功 |
| `409 EVENT_VERSION_CONFLICT` | 提供商事件已变化；清除旧预览，重新读取详情，由用户重新决定 |
| `409 DRAFT_VERSION_CONFLICT` / `DRAFT_STATE_CONFLICT` | 草稿被修改或不再可编辑；刷新草稿，不能静默覆盖 |
| `409 APPROVAL_EXPIRED` / `APPROVAL_ALREADY_DECIDED` | 停止操作，读取最新审批状态 |
| `422` | 字段、时区、日期、邮箱、类型或不支持的全天/循环事件非法 |
| `503 CALENDAR_TOOL_UNAVAILABLE` | MCP/提供商失败，保持站内草稿与审计，不伪装为空日历或成功 |

页面对 `create/update/cancel` 分别使用“新建会议”“编辑会议”“取消会议”，对待确认草稿使用不同于正式日程的视觉样式。按钮只依据服务端能力字段显示；每次打开详情和提交前重新取权威数据。离开页面或刷新后可通过草稿详情、任务详情和审批列表恢复状态，不重复提交外部动作。显示的参会人仅表示邀请目标，不得声称对方已同意或有空。

#### 2.1.8 专题验收与落地顺序

1. 先实现 Provider/Mock 的稳定事件版本、条件修改与条件取消及测试；确认通知语义、所有权边界和幂等键。
2. 实现受保护的操作草稿及迁移、RLS、版本 CAS、审批冻结、Checkpoint 恢复与 Worker 写工具白名单；真实写入仅发生在批准后。
3. 扩展只读详情能力字段，再接入日历页三个入口；在后端未支持前不显示编辑/取消按钮。
4. 测试重复点击、刷新恢复、版本冲突、连接失效、审批过期、拒绝、MCP 超时、执行后读回、参会人通知提示，以及 Mock/真实来源区分。

阶段二上线前不得将本文示例路径和字段写成“已实现”。旧的五个 GET、对话创建会议与逐项确认入口必须继续工作。

### 2.2 后续专题登记区

每个新增专题独占一个 `2.x` 小节，直接写入现状与目标、页面操作与对应接口、请求及响应契约、数据与权限边界、前后端实现顺序、兼容方案和验收项。未登记的专题不因出现在总计划标题中而自动进入开发范围。

## 3. 共通设计与交付约束

- 以真实代码和已实现接口作为现状依据；计划接口必须与已实现接口分开标注。
- 租户与用户身份由认证链路确定；资源访问、RLS、版本冲突和审计由后端保障，不能依赖前端按钮隐藏。
- 涉及外部写入的操作须明确审批、幂等、失败恢复和用户可见结果；前端不得把“已提交”“已批准”显示成“已执行”。
- 保持第01期已上线对话、审批、邮件、日历等流程兼容；新专题逐项列出需要回归的旧能力。

## 4. 计划推进与总体验收

1. 按专题确认业务范围和现有能力，补齐需决策的问题；未确定处标“待规划”。
2. 完成接口、数据模型、权限及副作用设计，评审后再实施后端和前端。
3. 以接口测试、权限/冲突/失败场景和页面回归结果更新专题状态；不能仅凭页面展示或接口示例宣布完成。
4. 每次新增或调整专题时，更新相应 `2.x` 小节的依赖、兼容和验收记录；保留与第01期接口的兼容说明。
