# 用户主动维护长期摘要与实体记忆（7.3）

## 范围与边界

写入入口只有长期记忆页面/用户设置表单经认证调用的管理API。没有聊天记忆意图、LLM提取器、候选卡片、自动确认或轮后自动落库。
主Agent与专家没有memory.write工具，Worker的MemoryRepository只有只读检索和既有使用记录写入能力。
聊天不能声称已经替用户保存偏好，应引导用户进入长期记忆页面。

本阶段支持长期摘要和结构化用户设置，不把邮件/日历/知识原文自动复制为长期记忆。
没有新增Embedding、Qdrant或pgvector依赖。用户设置保存为偏好，不修改连接权限或服务器APP_TIMEZONE。
实际按模型用途装配MemoryContextBundle及attempt级用量审计继续在7.4完成。

## 调用关系

```text
用户主动录入/编辑
 → MemoryView（完整表单）
 → POST /memories 或 PATCH /memories/{id}
 → MemoryService → MemoryLifecycleRepository → PostgreSQL pending记录
 → 页面回填服务端实际保存值，用户核对并勾选
 → POST /memories/confirm（memory_id + expected_version）
 → 来源/有效期复核 → 实体冲突时要求显式替换 → confirmed

普通回复/邮件草稿调用模型前
 → MemoryContextService → Worker MemoryRepository
 → SQL限定身份、confirmed、非敏感、未过期、有效来源
 → 既有相关性筛选与有界格式化 → Prompt
```

页面发生未保存修改后禁止确认旧记录。PATCH会立即退回pending，旧内容不继续生效；原删除令牌作废。
同一ID编辑只保存当前内容，审计保留版本/状态/来源/内容指纹，不额外复制历史敏感正文。

## 数据和迁移

`017_memory_manual_lifecycle`增加：memory_type、scope、entity_key/value、sensitivity、status、version、
confirmed_at、expires_at、source_kind/object_id/version、supersedes_id，以及带owner RLS的memory_item_revisions。
审计由数据库trigger记录创建、编辑、确认、覆盖、删除，只保留元数据与内容/实体指纹，不保存Prompt或正文副本。

旧记录显式映射：

- 旧is_sensitive映射normal/sensitive，保留旧字段并用数据库约束保持一致。
- 旧未删除手动记忆按此前“手动保存即生效”的语义回填confirmed，confirmed_at=created_at；不是模型替用户新增一次确认。
- 已删除记录映射deleted，不恢复旧正文。旧来源任务仅在真实归属匹配时回填版本；无法核实的记录标记revoked。
- 新写入默认pending，只有确认接口能使其生效。

纯手动来源kind=manual，业务对象/版本均NULL，不虚构run或对话。
source=user_input/user_confirmed保留旧枚举，表示人的录入/确认行为，不是模型提取来源。

## 实体和覆盖

scope固定user。支持三个明确key：

| key | 值 |
| --- | --- |
| timezone | IANA时区，如Asia/Shanghai |
| reply_style | formal / concise / friendly |
| contact | 单一常用联系人的name/email；不代表邮件发送批准 |

首版contact是单一默认联系人设置，不是批量通讯录或按名称自动合并。
说明content不能覆盖真实entity字段；Worker注入实体时使用校验后的结构值。
API校验时区/邮箱/长度/字段，拒绝额外字段及高危秘密；明显敏感标记不能被请求降为normal。
该确定性检查不是完备DLP，普通内容是否涉及敏感业务仍需用户正确分级；敏感内容即使用户确认也不进入模型。

同用户同key最多一个confirmed且未删除记录，部分唯一索引作为最后守卫。
确认/编辑/删除按用户事务锁串行；另以expected_version防止旧页面覆盖新值。
冲突返回MEMORY_ENTITY_CONFLICT及旧ID/版本，不返回旧敏感正文。
用户主动查看旧记录并明确提交replace_memory_id/replace_version后，旧行变superseded，新行保存supersedes_id。
旧行保留，不合并文本；过期/来源失效但仍confirmed的旧实体同样需要显式替换，不静默抢占key。

## 来源、失效与读取

仅允许手动、本人已完成任务和已授权知识文档引用，其他业务来源暂不开放。

- run：服务端固定实际run版本指纹；核验tenant/user、completed状态及其会话仍可见。兼容source_run_id，但不能填写不存在/他人的任务。
- knowledge_document：提供真实document_id与当前version_id；按同租户私有/共享、enabled、非敏感、外发许可、ready当前版本复核。
- manual：只有人的录入事实，不要求虚构业务对象。

数据库函数aegis_memory_source_accessible以SECURITY INVOKER运行，与API/Worker共用同一套来源谓词，不绕过RLS。
来源删除/撤权/失效/版本变更立即使下一次检索不再交付该记录，后台清理不影响即时授权。
source_available和prompt_eligible反映读取时事实，status不伪装成实时授权证明。

普通回复节点不再复用Checkpoint的memory_context字符串，而在真正模型调用前重新查当前记录。
邮件起草通过Workflow提供的只读回调，在首次调用和格式修复调用前分别重读；专家不直接做SQL，事实刷新失败不当作格式错误重试。
主路由、知识回答、邮件事实提取不因此获得长期记忆注入。并未替代7.4统一用途策略/结构化Bundle/调用attempt审计。
旧run_memory_usages仍按原格式记录，历史审计脱敏与管理扩展留待7.5。

## 部署与兼容

先停旧API写入与旧Agent Worker，备份后在Aegis_backend目录执行：

```powershell
D:\anaconda\envs\Aegis\python.exe -m alembic upgrade 017_memory_manual_lifecycle
```

再一起部署新版API、Agent Worker和前端。不能让旧Worker与新API混跑：旧读取条件不认识pending状态。
非管理员运行角色需具备新审计表INSERT/SELECT及来源事实所需读取权限，仍保持owner/tenant RLS。
不需要重新生成向量、修改Redis配置或增加模型开关。本次实现未升级现有业务数据库，迁移由部署者执行。

旧POST创建现在仅保存pending；旧content+source_run_id确认格式仍支持人的显式确认，但真实来源须可用。
PATCH必须携带expected_version及完整关键字段，缺失返回422，避免默认值默默清除敏感级别/来源/有效期。
降级会丢弃新字段/审计；若有无法用旧格式表示的未删除记录，downgrade主动拒绝，先人工导出处理，不能回退后意外注入待确认值。
