# 结构化计划与工具结果状态传递开发计划

> 目标：让主助手、日历专家、邮件专家及后续其他领域专家通过 LangGraph State 交接**结构化计划、可信工具结果和业务对象引用**，为多 Agent 协同奠定基础。本文是后续开发计划，除已标注“当前已具备”的内容外，不代表已经实现。

## 1. 设计目标与边界

主对话框适合处理自然语言、搜索、追问和推荐；邮件管理、日历确认等领域页面适合展示列表、编辑字段和提交明确操作。两类入口最终复用相同的领域工作流、Service 和 ToolGateway。

```text
自然语言对话
  → 主助手/根图选择领域工作流
  → 领域 Agent 生成受限计划
  → Workflow 调用 Service / ToolGateway
  → MCP 工具结果
  → 结构化结果与业务引用
  → 主助手生成最终消息、前端渲染卡片

领域页面按钮
  → 已明确的业务对象 ID
  → 对应领域 Workflow
  → Service / ToolGateway
```

约束如下：

- Agent 不直接访问数据库、MCP Server 或外部写入能力。
- Workflow 负责编排、分支、暂停和恢复；不承担 SQL、权限或工具网络调用细节。
- Service 负责业务读取/保存、事务、事件；ToolGateway 负责工具白名单、参数、连接、scope、租户和审计校验。
- LLM 可以提出受限计划，但不能决定越权调用、外部写入或跳过审批。
- State 不能保存完整邮件正文、附件内容、OAuth 凭据、LLM 思维过程或未经脱敏的工具原始响应。

## 2. 当前状态

当前已经具备：

```text
TaskGraphState
  → run_id、tenant_id、user_id、conversation_id
  → intent、workflow、selected_tool_name、selected_tool_arguments
  → tool_context、assistant_content

CalendarReadWorkflow
  → CalendarAgent 生成 ToolInvocation
  → ToolExecutionService 经 ToolGateway 调用日历工具
  → tool_context 进入最终回复

邮件页面后台任务
  → mail_extraction / mail_reply_draft / mail_send
  → 使用明确的 email_id / draft_id，不需要对话路由
```

当前尚未具备：

- 通用、可审计的 `plan` / `tool_result` / `artifacts` State 契约；
- 主对话框的 `MailQueryWorkflow`；
- 对话候选卡片持久化与“第一封”“这封邮件”等跨消息指代解析；
- 基于受限 LLM 结构化输出的根图路由。

## 3. 目标 State 契约

在保留现有稳定字段的基础上，逐步引入以下字段：

```python
class TaskGraphState(TypedDict, total=False):
    # 已有稳定身份与任务标识
    run_id: str
    tenant_id: str
    user_id: str
    conversation_id: str
    run_type: str

    # 根图路由
    intent: str
    workflow: str

    # 新增：经 Schema 校验的领域计划
    plan: dict[str, Any]

    # 新增：已脱敏、大小受限的工具结果摘要
    tool_result: dict[str, Any]

    # 新增：供消息卡片、页面跳转和后续指代使用的业务对象引用
    artifacts: list[dict[str, Any]]

    # 已有对话上下文与最终内容
    history: list[dict[str, Any]]
    memory_context: str
    assistant_content: str
```

### 3.1 `plan`

`plan` 是领域 Agent 的受控输出，不是工具调用已经成功的事实。例如：

```json
{
  "domain": "calendar",
  "action": "read_events",
  "tool_name": "calendar.list_events",
  "arguments": {
    "start_at": "2026-10-09T00:00:00+08:00",
    "end_at": "2026-10-10T00:00:00+08:00",
    "timezone": "Asia/Shanghai"
  },
  "risk_level": "read"
}
```

邮件查询计划示例：

```json
{
  "domain": "mail",
  "action": "query_messages",
  "tool_name": "mail.messages.search",
  "arguments": {
    "keywords": ["续约"],
    "received_after": "2026-10-05T00:00:00+08:00"
  },
  "risk_level": "read"
}
```

计划必须经过 Pydantic/JSON Schema 校验，并由代码确认工具在当前 Workflow 的白名单中。

### 3.2 `tool_result`

`tool_result` 只保存后续节点和最终消息所需的安全摘要。例如：

```json
{
  "status": "succeeded",
  "summary": "查询到 2 项日程",
  "events": [
    {
      "event_id": "...",
      "title": "项目同步",
      "start_at": "...",
      "end_at": "..."
    }
  ]
}
```

完整、可追溯的工具事实仍写入 `tool_calls`、`run_events` 和各领域业务表。State 不是审计数据库。

### 3.3 `artifacts`

`artifacts` 用于把领域对象安全交给消息展示层和后续任务，例如：

```json
{
  "type": "mail_candidates",
  "query_id": "mcq_01J...",
  "items": [
    {
      "position": 1,
      "email_id": "...",
      "subject": "2026 年服务续约确认",
      "sender_name": "李莉",
      "received_at": "..."
    }
  ]
}
```

Artifact 只保存稳定对象 ID 与脱敏展示字段，不保存完整邮件正文。卡片按钮必须使用 `email_id`、`draft_id`、`calendar_draft_id` 等稳定标识调用后端接口。

## 4. 分阶段实施

### 阶段 1：定义 Schema 与 State 字段

1. 为计划、工具结果和 Artifact 定义 Pydantic 模型；初期可先支持 `CalendarReadPlan`、`MailQueryPlan`。
2. 在 `TaskGraphState` 中加入 `plan`、`tool_result`、`artifacts`。
3. 制定序列化、大小限制、脱敏规则；在写入 Checkpoint 前校验。
4. 为每类模型编写序列化、非法字段和越界参数测试。

**验收：** 任一节点只能写入已声明的结构；不含敏感正文和凭据的数据可以跨 Checkpoint 恢复。

### 阶段 2：改造 `CalendarReadWorkflow`

将现有链路：

```text
CalendarAgent → ToolInvocation → ToolExecutionService → tool_context
```

迁移为：

```text
CalendarAgent.plan_read
→ state.plan
→ validate_calendar_plan
→ execute_calendar_plan
→ state.tool_result
→ build_calendar_artifacts
→ generate_reply
```

`CalendarAgent` 仍可以是确定性规则，不要求立即接入 LLM。工具实际执行仍必须走 `ToolGateway`。

**验收：** 查询日程和查询空闲时间可输出可审计的计划、工具结果和日历卡片引用；最终自然语言回复只消费可信结果。

### 阶段 3：新增对话结果引用持久化

新增迁移和 Repository，建议表名：

```text
conversation_message_artifacts
```

建议字段：

```text
id
tenant_id
user_id
conversation_id
assistant_message_id
run_id
artifact_type
query_id
payload                 # 脱敏 JSON
expires_at
created_at
```

它用于支持“第一封”“这封邮件”“刚才那个会议”等短期会话指代。候选对象的真实事实仍以领域业务表为准。

**验收：** 后端能按租户、用户和会话读取最近有效 Artifact；过期、越权或存在歧义时拒绝自动解析并要求用户选择。

### 阶段 4：实现 `MailQueryWorkflow`

新增：

```text
agent/workflows/mail/query_graph.py
```

建议流程：

```text
用户消息
→ MailAgent 生成 MailQueryPlan
→ state.plan
→ ToolGateway 调用 mail.messages.list / mail.messages.search
→ state.tool_result
→ build_mail_candidate_artifacts
→ 持久化 conversation_message_artifacts
→ SSE: mail_candidates_ready
→ generate_reply
```

前端将候选结果渲染为邮件卡片；用户在卡片点击“查看”“生成摘要”“加入待办草稿”“起草回复”时，复用现有邮件 API。前端不得直连 Email MCP Server。

**验收：** 用户输入“帮我找本周续约邮件”后可得到脱敏候选卡片；用户点击卡片操作后进入既有 `mail_extraction` 或 `mail_reply_draft` 链路。

### 阶段 5：升级根图路由

当前 `TaskGraphRouter` 主要使用关键词。后续采用：

```text
确定性规则缩小候选领域
→ LLM 输出受 Schema 校验的 IntentPlan
→ WorkflowRouter 校验允许的 Workflow
→ 进入领域子图
```

规则层必须始终控制：

- 写操作不可仅由 LLM 决定；
- 可见工具白名单；
- 参数范围；
- 用户连接与 scope；
- 租户归属；
- 审批要求。

**验收：** LLM 输出未知 Workflow、未注册工具或不合法参数时，根图安全回退、追问或返回失败，不执行外部操作。

### 阶段 6：统一领域子图协议

每个领域子图逐步收敛为：

```text
输入：state.plan 或明确业务对象 ID
执行：Service / ToolGateway
输出：state.tool_result、state.artifacts、assistant_content（可选）
```

典型对应关系：

| 子图 | 输入 | 输出 |
|---|---|---|
| `CalendarReadWorkflow` | `CalendarReadPlan` | 日程/空闲时间 Artifact |
| `MailQueryWorkflow` | `MailQueryPlan` | 邮件候选 Artifact |
| `MailExtractionWorkflow` | 明确 `email_id` | 提取结果引用、待办候选 |
| `MailReplyDraftWorkflow` | 明确 `email_id` | `draft_id` Artifact |
| `CalendarConfirmationWorkflow` | 会议计划 | 草稿/审批/事件引用 |

### 阶段 7：多 Agent 协同

在上述协议稳定后，主助手仅选择领域与整合最终回复：

```text
MainAgent
  → CalendarAgent
  → MailAgent
  → TodoAgent
  → ResearchAgent
```

协作通过 State 的 `plan`、`tool_result` 和 `artifacts` 完成，不让 Agent 之间以不受约束的自然语言互相指挥。

```text
MainAgent 写入任务目标和领域选择
→ Domain Agent 写入受限 plan
→ Workflow / Service 写入可信 tool_result 与 artifacts
→ MainAgent 基于可信结果生成最终回复
```

## 5. 推荐实施顺序

```text
1. Plan / ToolResult / Artifact Schema
2. CalendarReadWorkflow 状态迁移
3. conversation_message_artifacts 数据表、迁移、Repository
4. MailQueryWorkflow
5. 前端候选邮件卡片与卡片操作
6. 受限 LLM 根图路由
7. 会议安排、邮件起草、待办等领域子图继续迁移
```

每一步均应有独立单元测试、SSE 事件测试和端到端验证，并保持现有页面按钮入口可用，避免一次性重构整个 Worker。
