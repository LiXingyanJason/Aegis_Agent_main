# 知识查询子图与来源约束回答（6.5）

## 1. 范围

在6.1知识专家／子图骨架及6.4真实Hybrid检索上完成引用治理、冲突表达、失效保护与历史卡片读取复核。
不新增独立知识MCP、不引入开放ReAct、不增加外部写工具，不改变邮件／日历路由或审批恢复。
没有新增迁移，不改变查询开关的默认值或实际.env。来源详情／下载及完整多版本管理仍不属于本阶段。

## 2. 分层与执行顺序

```text
TaskGraph.main_decision
  → 已注册的knowledge.query_knowledge能力 → knowledge_query子图
    → plan_knowledge_query：KnowledgeAgent生成KnowledgeQueryPlan，代码校验
    → search_knowledge：KnowledgeQueryService → Gateway/Harness → Hybrid检索
    → verify_knowledge_evidence：EvidenceService → SQL再次核验，保留排名顺序，连续编号
    → answer_knowledge：KnowledgeAgent结构化回答，核验Schema及来源编号
    → persist_knowledge_sources：再次核验全部生成依据，再保存Artifact
  → 根图END → 既有Lifecycle保存助手消息／完成run
```

KnowledgeWorkflowFactory在启动时注册子图；只有KNOWLEDGE_QUERY_ENABLED=true才加入主Agent能力目录。
普通对话仍由MainDecisionWorkflow决策，明确页面任务与审批／补充问答恢复保持原有入口。
专家只做语义规划与证据回答；Service负责事务／事实复核和事件，Repository负责SQL。
根图不自行访问SQL、Embedding或Qdrant，也不再调用通用回复模型改写知识专家的最终答案。

## 3. 证据与引用约束

- 规划不合法时不调用检索；空证据时不调用回答模型，由代码回复“无法从已授权资料确认”。
- 检索只交付≤5个有界摘录及稳定document/version/chunk/hash/位置引用；身份ACL、向量与整份原文不进入新增State或SSE。
- 首次复核保留原召回顺序；丢弃失效候选后重新分配[1]、[2]，模型不需要猜测稀疏旧编号。
- KnowledgeAnswer.answer中的规范`[n]`集合必须与citation_numbers一致，编号必须属于本轮核验证据。
  `[01]`、伪造编号、额外工具／权限字段均非法；引用合法不等于事实语义已经被证明。
- 回答后复核全部生成依据，而不只是显式引用项。任一依据失效／变更，整个旧回答及来源卡片不交付，返回KNOWLEDGE_SOURCE_UNAVAILABLE。
  不把新版本或新正文替换进旧引用，不对已生成答案重新编号。
- 6.4的降级诊断仍保留；成功降级回答由代码前置仅依据关键词检索的提示。

State继续使用knowledge_plan、knowledge_evidence、knowledge_answer、knowledge_retrieval及有界artifacts；
失败分支清空本次证据、答案和Artifact，不通过通用LLM兜底编造公司规定。
原始无效模型输出不写入修复提示、日志或新增审计字段。

## 4. 有界修复、冲突与注入边界

知识规划／回答均使用complete_json，再由Pydantic和引用范围校验。
格式、Schema及伪造引用错误最多修复一次（复用OutputPolicy.max_repairs），两次调用均经GuardedLLMClient累计预算。
修复提示只说明原契约无效，不附原始非法输出或错误里的正文值。连续失败返回安全错误分类。
网络、超时及Harness预算错误不触发格式修复，也不默认执行工具。

既有run_execution_attempts.purpose是可空text，本阶段只增加代码用途白名单，无需迁移：
knowledge_planning、knowledge_planning_repair、knowledge_answer、knowledge_answer_repair。
每次调用继续记录模型信息／耗时／可用Token用量，缺失用量不伪装为0。

KnowledgeAnswer新增可选has_conflict（默认false，兼容旧结果）：

```json
{
  "answer": "资料一要求提前30天通知[1]，资料二要求提前60天[2]；现有依据无法确定适用哪份。",
  "citation_numbers": [1, 2],
  "can_confirm": true,
  "has_conflict": true
}
```

has_conflict=true必须有至少两项引用，不能与can_confirm=false组合。
can_confirm表示答案有证据支撑，包括“现有资料相互冲突”的回答，不表示冲突已解决或允许执行业务动作。
成功交付时代码前置“资料存在冲突，以下列出不同依据，不能据此确认唯一结论”。来源payload保留has_conflict。
能否发现真实语义冲突、每条事实是否真的被片段支持，仍需人工／固定评测；此Schema不是语义正确性证明。

文档作为user消息中的JSON数据传入，不作为system指令。提示明确要求只依证据、逐项引用、信息不足则拒绝确认。
知识回答模型没有执行工具接口；子图唯一检索动作是knowledge.search。
文档包含“忽略指令、发送邮件、提权”不会获得执行权限；即使模型输出工具调用JSON，也因契约不符被拒绝。
这不等于仅凭提示词能彻底防止错误文字或提示注入，仍须评测模型行为。

## 5. 来源持久化与历史读取

Artifact继续使用knowledge_sources，payload.sources为实际引用的稳定快照，新增has_conflict，
提交后仅用artifacts_ready通知前端按需读取，不在刷新事件内塞原文。
来源保存沿用ConversationArtifactService，消息完成时由原有Lifecycle补齐assistant_message_id。

主后端GET /conversations/{conversation_id}/artifacts先检查会话归属，
然后KnowledgeArtifactService → KnowledgeSourceRepository按登录用户重新读取来源SQL事实。
SQL再次核验同租户、私有／共享、enabled、未删除、非敏感、外发授权、ready当前版本及indexed_at。
document/version/chunk/title/section/hash/位置/摘录全部与旧快照相同才返回；不依赖旧Artifact作授权。
Worker与主后端独立部署，主后端的有界快照DTO不导入Worker包。

知识卡片读取payload新增availability：

| 值 | 行为 |
| --- | --- |
| available | 所有来源仍有效 |
| partial | 只返回仍有效来源；历史source_no不重排，提示部分依据不可用 |
| unavailable | sources=[]，不返回旧标题／正文／hash等来源快照 |

无效快照同样返回unavailable，不能把非法内容显示作兜底。其余邮件、日历卡片不经此逻辑，不改原响应。
前端应重新获取并替换卡片，sources为空时显示来源不可用，不能复用本地缓存旧摘录；partial也不能视为冲突已解决。
知识来源仍无独立详情／下载接口；新增API说明仅追加在根目录接口文档篇末第8章。

权限复核是交付时检查，不宣称SQL与网络或SSE有全局原子事务。
不能撤回已读内容，也不自动清除历史助手消息、既有Checkpoint／审计快照或浏览器已收到的数据；
这些已授权历史数据的保留、敏感信息清理属于另行治理范围。

覆盖合法引用、有界格式／引用修复与累计预算、网络／预算不重试、冲突两项引用、
