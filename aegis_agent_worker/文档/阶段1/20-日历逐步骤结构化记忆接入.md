# 日历逐步骤结构化记忆接入

实施日期：2026-10-19。补充阶段7.4，不向整个CalendarAgent开放自由文本长期记忆。

## 1. 边界与调用用途

| 步骤/用途 | 允许的记忆 | 作用与限制 |
| --- | --- | --- |
| calendar_planning：日期规划/查询计划 | timezone实体，最多1条 | 代码确定解释时区，并用同一时区生成当前时间、模型提示和原文时间校验 |
| 空闲查询与冲突校验 | 不读取额外记忆 | 沿用已校验计划的时区与时间点；空闲事实只由工具结果及确定性代码判断 |
| calendar_draft_personalization：会议草稿生成及候选推荐 | timezone、meeting_preferences实体，最多2条 | 只辅助可信候选排序与草稿措辞，不改候选、时长、参会人或明确指定时段 |
| calendar_recommendation：独立候选推荐方法 | 同上，最多2条 | 调用方须显式绑定可信run/用途；单候选快速返回不调用模型，也不读取记忆 |
| 批准后创建日历 | 无 | 只读取已批准草稿版本，既不读长期记忆，也不再次调用LLM |

主路由、邮件查询/事实提取/信息收集、知识检索/证据回答和审批的记忆边界不变。
日历三个用途不接受长期摘要、联系人、回复语气，亦不从“周一上午不安排会议”等自由文本说明自动提取规则。
`MemoryContextBundle`本身也校验日历用途仅能携带允许的结构化实体，同一实体key不能有多个生效值。

## 2. 时区优先级

```text
本轮明确的IANA/常用时区名称
  > 当前已确认、非敏感、未过期且来源仍有效的timezone实体
  > CalendarAgent配置时区（默认Asia/Shanghai）
```

支持IANA名称、北京时间/上海时间/中国时间、东京时间、纽约时间、伦敦时间、UTC以及整小时UTC±偏移。
出现多个不同的时区声明则安全澄清，不自行猜测。此解析仅处理日期参数，不参与主意图/工具路由。
ISO时间中明确的Z/偏移始终保留其真实时间点；显示可换算为本次解释时区，不能把03:00Z当成本地03:00。
明确指定时区时不读取已被覆盖的时区记忆，也不伪造该条记忆的使用审计。

例如已确认 `Asia/Tokyo`：

- “2026-10-20 15:00～15:50安排50分钟会议”：按东京时间规划。
- “北京时间2026-10-20 15:00～15:50安排50分钟会议”：仍按北京时间。
- “2026-10-20T03:00Z～03:50Z”：时间点不变，可显示为东京12:00～12:50。

无偏移的夏令时不存在/重复本地时钟要求用户明确偏移，不用记忆猜fold。
格式修复前重新查SQL并重建时区/当前时间，校验也使用本轮同一个代码解析结果，不保存上次非法输出或旧记忆摘录。
生成后的CalendarDecision保留已核验的timezone及时间点，传递到工具计划、冲突计算、草稿、确认卡片与最终写入。
规划完成后即使记忆改变，草稿推荐不得重新解释原计划日期；用户批准后也不会因为记忆变化修改时间。

## 3. 会议软偏好契约

用户在长期记忆页面选择“结构化用户设置 → 会议软偏好”，手动填写并核对确认：

```json
{
  "key": "meeting_preferences",
  "preferred_time_of_day": "afternoon",
  "avoid_weekdays": [1],
  "strength": "soft"
}
```

- preferred_time_of_day：any / morning / afternoon / evening。
- avoid_weekdays：不重复的1～7整数（周一～周日），拒绝布尔、字符串、越界值。
- strength：只能为soft；不接受硬性权限、工具名称、执行指令或其他字段。

实体说明content只是用户管理时的说明，不用它覆盖结构化字段。仍走已有pending → 用户核对确认流程。
结构化实体的content现为可选；省略/空白时由主后端生成规范说明，修改结构字段后会重新生成。
长期摘要仍必填。详情content_is_generated只是编辑提示，未增加存储字段或自动确认；详见接口文档篇末第17章。
同一用户同一key只有一个确认值，更新/替换沿用现有版本冲突及显式覆盖审计，不能由专家自动创建或修改。
“偏好下午”不会屏蔽上午候选，避开周一不代表周一不可用；本轮明确要求优先，LLM只能在可信slot_id集合中选择。
真正保存草稿时继续校验原计划时长、明确参会人、明确时段；工具scope、审批及幂等仍由原代码保证。

## 4. 调用关系与治理

```text
CalendarWorkflowFactory（注入MemoryContextService）
  ├─ CalendarPlanningWorkflow
  │    → memory_call_scope(calendar_planning)
  │    → CalendarAgent.plan_calendar
  │    → GuardedLLMClient.complete_prepared
  │         → Harness预算/attempt → SQL重读 → 结构化Bundle
  │         → 纯消息工厂：代码解析有效时区/当前时间
  │         → 低优先级数据装配、大小检查、版本/来源复核审计 → 模型
  │    → 同时区原文/Schema校验 → CalendarDecision → 只读工具/冲突检查
  └─ CalendarConfirmationWorkflow.generate_calendar_draft
       → memory_call_scope(calendar_draft_personalization)
       → CalendarAgent.generate_meeting_draft → 同一Guarded调用链
       → 候选/草稿校验 → 用户批准 → 固定版本写入（无记忆/无LLM）
```

`complete_prepared`只是已有受治理调用的纯消息工厂接口，不重复实现模型网络通信或Harness，不在专家中读SQL。
上下文作用域和Bundle仍是单次调用局部数据，不向Checkpoint保存可重复注入的摘录。
独立recommend_meeting_slot方法使用calendar_recommendation用途；生产会议确认节点已把推荐与草稿生成合成一次调用，不额外增加推荐模型调用。

额度继续来自PolicyProvider，日历语义版本为`calendar-memory-v1`：
候选50条、规划最多1条/推荐最多2条，同时受每条400字符、总1500字符/6000字节和本次输入剩余额度约束。
字符、Token和失败策略与7.4一致；Token未知保持null，配置Token硬上限却无可信估算时不注入。
记忆查询故障可回退配置时区/无偏好；预算或审计错误不作格式重试，不绕过审计发出带记忆请求。
每次首次、修复、恢复后的模型调用重新复核SQL生命周期/来源，记录真实attempt、用途、记忆ID/版本/来源及数量，不记录完整Prompt。
