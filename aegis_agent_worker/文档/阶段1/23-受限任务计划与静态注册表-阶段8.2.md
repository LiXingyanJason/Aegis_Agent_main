# 8.2 受限任务计划与静态注册表

## 已完成与未开放的边界

已实现协同工作流内由CooperationPlanner提出CooperationPlan、静态能力/实际节点双重绑定、Schema及DAG校验、输入引用复核、Checkpoint绑定与逐步进度引用。MainAgent只选择并核验交接目标，普通单领域请求不生成多步计划。

**本阶段不是8.3通用调度器。** 当前只允许完整的“邮件时间要求→日历候选→会议草稿”执行配置，验证通过后仍由8.1固定子图执行。其他DAG即使结构合法，也不能默认执行第一步或退回固定计划，而是澄清。没有choose_next、动态子任务、并行、递归、任意图拓扑或自动批准。

## 真实注册节点与目录

CooperationWorkflowFactory在开启计划功能时，注册下列预构建子图及独立的CooperationCapability：

| workflow（根图实际注册节点） | 领域 | 输出契约 | 输入契约 |
| --- | --- | --- | --- |
| cooperation_mail_requirements | mail | MailRequirementsV1 | user_request，可加已核验verified_target |
| cooperation_calendar_candidates | calendar | CalendarCandidatesV1 | 邮件步骤的MailRequirementsV1 |
| cooperation_meeting_draft | calendar | MeetingDraftV1 | 邮件步骤的MailRequirementsV1及候选步骤的CalendarCandidatesV1 |

这些节点复用现有邮件查询/提取及日历候选/草稿执行节点，不新建MCP或复制Service业务逻辑。步骤目录与普通ConversationCapability分离：主路由仍只能选择mail.arrange_meeting_from_mail→mail_calendar_meeting，页面run_type也不能直接指定上述内部节点。

GraphRegistry维护真实子图对象与目录声明；CooperationRegistry对其建立不可变快照，检查父入口能力和实际节点存在、领域与输出契约一致。模型只收到安全目录描述，没有数据库连接、函数名、代码对象或导入路径。

三个输出标签绑定agent/contracts/cooperation_outputs.py中的真实Schema，复用TaskStepResult并进一步限制各阶段字段。邮件结果不能夹带草稿/审批引用，候选结果不能覆盖邮件计划或伪造审批，草稿结果不能替换来源和候选快照。

## CooperationPlan例子

```json
{
  "version": 1,
  "steps": [
    {
      "step_id": "lookup",
      "workflow": "cooperation_mail_requirements",
      "depends_on": [],
      "inputs": [{"kind": "task", "name": "user_request"}],
      "expected_output": "MailRequirementsV1"
    },
    {
      "step_id": "slots",
      "workflow": "cooperation_calendar_candidates",
      "depends_on": ["lookup"],
      "inputs": [{"kind": "step", "step_id": "lookup", "output_contract": "MailRequirementsV1"}],
      "expected_output": "CalendarCandidatesV1"
    },
    {
      "step_id": "draft",
      "workflow": "cooperation_meeting_draft",
      "depends_on": ["lookup", "slots"],
      "inputs": [
        {"kind": "step", "step_id": "lookup", "output_contract": "MailRequirementsV1"},
        {"kind": "step", "step_id": "slots", "output_contract": "CalendarCandidatesV1"}
      ],
      "expected_output": "MeetingDraftV1"
    }
  ]
}
```

step_id可使用符合规则的稳定短标识，不要求一定叫lookup/slots/draft；代码按已注册workflow绑定8.1固定阶段，不靠模型标签执行工具。

inputs只有两类符号引用：task.user_request和step输出。若主决策已经通过卡片工具解析并核验了目标邮件，首步还必须包含`{"kind":"task","name":"verified_target"}`；没有已核验目标时，禁止此引用。实际对象ID/版本只从可信handoff及业务源读取，不能写进计划伪造另一个目标。

计划不包含instruction全文、邮件正文、工具参数、SQL、tenant_id、user_id、provider_connection_id、审批决定、完成状态或可自由指定的对象ID；额外字段拒绝。精确主题仍可不带target，由8.1查询定位唯一邮件，不会在规划阶段默认挑选邮箱第一封。

## 校验与执行入口

```text
MainDecisionWorkflow
  原有候选/目标/卡片核验
  → assemble_agent_handoff
  → 原路由审计
  → TaskGraph复核入口workflow
  → mail_calendar_meeting
      → plan_cooperation（开关开启时，CooperationPlanningWorkflow子图）
          → CooperationPlanner.plan → complete_json → CooperationPlan
          → CooperationRegistry.validate
          → 独立规划审计
      → 计划成功才进入8.1固定执行节点
      → 失败则返回结构化澄清并结束，不进入业务工具链
```

职责重构后MainDecisionWorkflow不再注入CooperationRegistry、不判断协同工作流名称，也不修改领域计划。CooperationPlanner封装提示词及有界结构化修复；CooperationPlanningWorkflow封装生成、注册表验证、状态装配及审计，可由其他协同入口装配。Service仅持久化审计，不处理LLM。Factory开启规划但未显式提供planner时拒绝装配；生产复用原GuardedLLMClient及PolicyProvider，不另建通信或预算。

代码依次检查：

1. Schema、步骤/依赖/字节上限、唯一step_id、标识格式、字段白名单。
2. workflow同时存在于协同步骤能力目录及根图节点集合，不允许目录外工具、模型临时节点或仅注册了普通工作流就冒充协同步骤。
3. 依赖存在、不自引用、不重复、无环；Kahn排序只用于确定性校验和记录顺序，不是运行期调度循环。
4. 输入引用只能指向声明的依赖，输出契约与生产者/消费者一致；依赖不得无输入用途、输入不得偷偷引用未声明依赖。
5. verified_target只能引用已核验目标，且目标存在时不可忽略它改为泛化查找。
6. 当前执行配置必须是完整三个注册步骤，顺序满足mail-calendar-meeting-v1；不能缺一步、重复一步或加入额外步骤。

格式/Schema错误最多按原OutputPolicy修复一次，首次和修复均经过GuardedLLMClient，累计模型次数、活跃时长和用量。修复只给安全字段路径/错误类型，不附原始非法输出。网络/预算错误不当作格式错误重试。DAG、注册、来源引用或不支持的组合直接澄清，不补造默认计划。

计划失败发生在邮件/日历业务调用之前。协同子图返回cooperation_clarification={code,question}、cooperation_error、unavailable状态和assistant_content，根图沿原协同分支结束并由既有收尾持久化回复；不篡改已验证的main_decision/handoff，也不把workflow改写成clarify。主决策为确定指代而进行的原有站内卡片只读调用，仍按独立白名单/额度核验；它不属于计划步骤，也不能证明邮件/日历已执行。澄清正常形成助手回复，本轮run可以completed，但这只表示交互结束，不代表会议已创建。

## 状态、恢复与审计

- cooperation_plan保存受校验计划，不另存用户全文。
- cooperation_plan_binding保存catalog_version、catalog_digest、plan_digest、policy_version、execution_profile、确定step_order及代码phase_steps映射。binding由代码产生，不接受模型填写。
- cooperation_progress按计划step_id保存状态与如`cooperation_results.mail_requirements`的结果引用，不复制结果正文；cooperation_current_step记录当前待处理/等待确认步骤，cooperation_status区分planned/in_progress/waiting_confirmation/completed/rejected/unavailable。
- 实际结构化结果仍按8.1固定阶段存入cooperation_results。结果按真实输出Schema及字节上限复核；消费依赖前检查已完成状态，业务身份/来源/连接/审批仍由Service/Gateway复核，进度字段不是授权证明。
- 每次消费和恢复复核计划、目录/策略版本及摘要绑定，不从Checkpoint提取一份旧全文当新授权。新计划不一致抛稳定路由错误，阻止继续执行；不重规划或静默替换目录。
- 暂停保存在同一run_id/thread_id的嵌套Checkpoint，批准或用户补充恢复不重新从START规划；页面直达任务绕过主路由/计划，单领域普通对话不增加规划调用。
- 8.1旧Checkpoint没有新字段时按原流程恢复，旧v3预算版本/余额不升级；新计划入口和内部适配子图则必须有已验证计划，不将兼容逻辑当作新任务的免检入口。

main_decision_completed仅报告主路由，不再携带新生成的cooperation_plan摘要；随后协同工作流发布独立cooperation_plan_completed事件，payload仅含outcome、repair_count、step_count、plan_digest、catalog_version/digest、policy_version和duration_ms。规划失败不把原路由审计改成失败；网络/预算异常记录model_failed规划元数据后仍按原异常分类失败，不作格式重试。不发布完整计划/Prompt、原始输出或邮件原文。模型用途仍为cooperation_planning/cooperation_planning_repair，逐次记录到既有run_execution_attempts，不注入个性化记忆，Token缺失仍unknown。

目录版本为cooperation-catalog-v1；摘要还绑定实际目录内容，不能仅保留版本名称却换节点。计划摘要绑定其校验后的序列化快照；等价重排可能有不同摘要，但在相同目录下得到相同确定顺序，不将摘要当业务授权。

## 策略、配置与兼容

额度由PolicyProvider.current().cooperation集中提供：cooperation-plan-v1，最多6步、每步5个依赖、计划8000字节、单步结果8000字节、总结果24000字节。Schema结构上限不等于已经支持所有6步组合；当前配置只放行上述3步。

Worker配置：

```dotenv
FIXED_COOPERATION_ENABLED=true
COOPERATION_PLANNING_ENABLED=true
```

第二个开关默认false；单独开启会启动校验失败，不能绕过固定执行链。新任务使用harness-v4-cooperation-plan；同时启用知识查询时为harness-v4-cooperation-plan-knowledge。原v1/v2/v3策略保留，v4不扩张工具白名单，模型10次、工具8次及原超时不变。增加的规划和修复也计入10次，不自动扩容。

无需新依赖、迁移或API/run_type，仍需已部署020和8.1工具/连接权限。部署前停Worker并处理在途任务，更新代码、按需配置后重启；本次不自动编辑.env或启动服务。已暂停的旧8.1审批可在新版本按原策略恢复，新8.2计划任务未结束前不要关闭计划开关、删除步骤节点或变更目录，否则绑定复核会拒绝恢复。

前端无需新增页面/工具调用。继续复用会议草稿、approval_required、失败提示及原任务状态；可忽略新增规划审计事件，不从计划/进度触发批准或外部写入。接口补充位于迁移后的`Aegis_backend/文档/阶段1/第01期-接口设计.md`篇末第20、21章。

兼容边界：保留原find_source_mail/extract_and_handoff/calendar_meeting及审批节点名称，旧8.1审批Checkpoint保持兼容。迁移前在主决策已生成的有效计划在新入口重新校验后复用，不重新规划、不重置进度/预算或重复规划审计。不要在旧主决策尚待执行已移除的plan_cooperation节点时热切换；部署前排空这类在途任务，再停止Worker升级。此次迁移不保证任意旧节点中断点的热恢复。
