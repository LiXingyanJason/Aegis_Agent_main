# 8.3 协同图调度与结果汇总

> 2026-10-20更新：调度成为唯一执行链路，开发期固定路径、三个递进开关、v3～v5协同策略及旧图恢复已删除。本文保留历史实施过程，当前结构、唯一配置和不兼容升级门禁以[8.3A部署指南](25-阶段8唯一链路收敛与部署.md)为准。新事件仅scheduled，本次不再修改前端。

## 实施范围

已实现计划驱动的串行调度，不再把新调度任务直接送入整条8.1固定图。MainDecisionWorkflow仍只路由，CooperationPlanner仍只提出受限计划，CooperationScheduler按代码注册的条件边选择步骤，不动态导入、生成图或递归生成子任务。

第一版目录仍只放行完整“邮件时间要求→日历候选→会议草稿”配置。调度器可按依赖选步，但不意味着已经开放任意跨领域组合、并行或开放式ReAct。新增业务步骤仍需真实子图、输入/输出契约、注册及相应权限测试。

## 图与职责

```text
main_decision：核验交接并审计
  → mail_calendar_meeting
      → begin_cooperation_schedule：固定调度版本
      → plan_cooperation：已有有效计划则复用，否则生成并验证
      → validate_schedule：复核目录、计划、策略绑定
      → choose_next：传播依赖失败，选择尚未执行且依赖均succeeded的步骤
          → cooperation_mail_requirements
          → cooperation_calendar_candidates
          → cooperation_meeting_draft（保存草稿→中断→审批恢复→原写入服务）
      → verify_result：Schema/来源/快照/审批事实复核→提交结果→choose_next
      → finish_cooperation：确定性部分结果汇总
```

三个步骤通过静态条件边分派到真正编译的子图，而非由模型函数名调用或根据字符串动态构图。相同计划及目录按绑定的拓扑顺序串行执行。当前max_parallel固定为1；没有并行共享草稿、同一对象竞态或子计划递归。

主要代码：

- `agent/workflows/cooperation/scheduler.py`：选择、提交前复核、依赖阻断、汇总。
- `agent/workflows/cooperation/fixed_meeting_workflow.py`：复用领域节点，保留旧固定恢复路径；新步骤结果暂存而不是提前提交成功。
- `agent/workflows/cooperation/step_execution.py`：稳定故障转换及步骤审计上下文，不自动重试，不捕获LangGraph中断/进程取消。
- `service/cooperation/fixed_meeting_service.py`：任务可执行状态、来源/草稿复核、用量与事件持久化；无LLM或调度逻辑。
- `repository/cooperation_repository.py`：有tenant/user/run过滤的SQL事实；审批状态及草稿版本必须匹配。
- `harness/cooperation_scope.py`及HarnessExecutor：在现有attempt.risk_flags中附加受限step_id/plan_digest标签，不改变权限或预算。

## State与验证顺序

1. 原有cooperation_plan/binding、目录摘要、策略版本继续生效；增加cooperation_scheduler_version固定本次执行引擎。未通过计划校验不调用业务工具。
2. choose_next记录当前step_id、running状态、工作流和开始时间。已有终态不能只凭进度标志跳过，必须有对应Schema结果及result_ref；同一步已登记执行时不再次分派。
3. 子图输出先存cooperation_pending_result。邮件/候选成功在verify_result后才写cooperation_results及cooperation_progress，并发布成功步骤事件；不会先向前端声称成功再验证。
4. 草稿已实际保存时可发布waiting_confirmation并暂停，pending结果和waiting进度保存在嵌套Checkpoint中，尚不算完成。批准/拒绝后生成终态结果，再复核来源、候选摘要、草稿/审批ID、用户归属和版本。
5. verify_result拒绝伪造来源、候选快照变化、外部状态与结果不符；错误只交付unavailable结果，不交付原暂存候选/草稿结果。正文不进入汇总、审计或长期记忆。
6. 最终cooperation_summary列出completed_steps、failed_steps、blocked_steps及每步工作流/状态/引用/原因；使用确定性模板生成失败提示，不增加额外LLM总结调用，不编造事实。

步骤状态包括pending/running/waiting_confirmation/succeeded/completed/rejected/unavailable/blocked。领域结果仍使用既有TaskStepResult契约；blocked仅是调度状态，不伪造一份“执行成功”的领域结果。历史已完成步骤是当时已验证的执行记录，不代表来源永久有效；后续领域消费和最终写入仍重新核验授权。

## 故障、取消与写入安全

- 单步骤稳定故障（模型、工具、预算、超时、格式或结果校验）转为unavailable，保留原稳定错误码；依赖它的pending步骤递归标为blocked，不继续调用下游工具。已完成步骤保留为可追踪部分结果。计划自身无效沿用8.2结构化澄清。
- 不对协同步骤设置自动重试。Harness原单次超时、累计调用/活跃时长预算及模型格式修复继续有效，额度不随步骤切换或审批恢复而重置。需要人工重新发起时是新任务，不在原任务重置余额。
- choose_next及领域节点边界读取数据库任务状态；已取消抛EXECUTION_CANCELLED，Orchestrator返回cancelled而不覆盖数据库为failed/completed。进程asyncio取消直接传播，不生成成功汇总。本次不新增全局取消API或取消按钮。
- 取消是执行边界检查，不承诺撤回已经发给供应商的网络请求或撤销已完成写入。写入前SQL还要求任务running、真实用户/租户、批准状态、未过期且草稿版本一致；审批记录和工具Gateway仍是写入授权来源，主Agent/调度器不拥有批准权。
- 原外部执行登记及稳定幂等键`calendar:{approval_item_id}:1`保持不变。写入超时/结果不确定时不自动重发；不得把“任务失败”解释成“供应商一定未写入”，应核对现有执行记录/提供商。
- 已执行步骤和verify_result之间都有Checkpoint。离线故障注入验证：批准写入后结果审计失败，再恢复只重做verify_result，不重新查询、起草或写入。若进程恰在外部写入与Checkpoint之间崩溃，仍依靠原外部执行唯一登记及提供商幂等边界阻止重复，不宣称跨网络 exactly-once；不确定执行不得人工删除登记后重发。

## 用量与SSE

逐调用仍写run_execution_attempts；协同调用额外附加`cooperation_step:<step_id>`及`cooperation_plan:<digest>`风险标签。Service按可信run/tenant/user和两个标签统计每步模型/工具次数、总Token；不靠工作机/数据库时钟范围猜归属，也不改purpose含义。任何模型调用缺total_tokens时聚合Token为null/unknown；没有模型调用也不伪装成0 Token。

cooperation_step_metrics保存上述安全统计、source版本引用、status、issue_code、result_ref、wall_duration_ms。wall_duration_ms包含可能的人工审批等待，不能当成纯模型/工具耗时或Harness活跃预算；逐次执行时间仍从attempt表分析。

新增可选事件：

- `cooperation_schedule_step_completed`：校验后的step_id、workflow、status、稳定原因、目录绑定引用、来源引用及用量摘要。
- `cooperation_completed`：整体status及部分结果列表，不代表所有步骤成功，更不代表任意会议已写入。

沿用cooperation_step_completed、approval_required、助手消息和原卡片。前端可忽略新增事件，不从其触发工具、重试或批准；waiting/unavailable/blocked/rejected不能显示为“成功”。事件持久化可能在故障恢复时重复通知，应按run/event_no处理；不能把事件投递当外部副作用的exactly-once证明。接口补充在`Aegis_backend/文档/阶段1/第01期-接口设计.md`篇末第22章。

## 开关、版本与兼容

```dotenv
FIXED_COOPERATION_ENABLED=true
COOPERATION_PLANNING_ENABLED=true
COOPERATION_SCHEDULING_ENABLED=true
```

三个开关默认false，缺少前置开关时启动校验拒绝。只有新调度开关开启才进入8.3；仅开启前两项仍走8.2校验计划后固定执行。

新任务策略为harness-v5-cooperation-schedule（知识查询同时开启则harness-v5-cooperation-schedule-knowledge），cooperation-schedule-v1：最多6步/每步5依赖、最大深度6、并行1；计划8000字节、单结果8000字节、总结果24000字节。模型10次、工具8次及原单次/总活跃超时不变。原v1～v4策略全部注册保留，恢复不升级或重置预算。

原find_source_mail/extract_and_handoff/calendar_meeting等固定节点仍存在；旧8.1/8.2暂停任务没有scheduler标记时按旧路径恢复，不中途切换执行引擎。新调度任务在途时不能关闭调度/规划开关、移除内部步骤或变更目录。8.2主决策规划节点迁移的排空要求继续有效；不支持任意旧节点热切换。

无需新增依赖、数据库迁移、API/run_type、Artifact类型或前端页面，仍需现有020、正确连接及工具权限。未修改真实.env、重启服务或调用真实模型/MCP。8.4真实效果对比和渐进启用仍待实施。
