# 目标、风险约束与混合协同编排（阶段8.3D，2026-10-20）

## 为什么调整

当目标唯一确定全部步骤时，让LLM重复生成同一条DAG只增加延迟和格式失败点。本次不为体现Agent而保留无意义推断，也不通过取消事实/审批前置条件制造自由度。

采用一套执行引擎、两种规划来源：路径唯一时由代码构造计划；存在替代生产者或可用可选输入时由LLM选择计划。两者都必须通过同一注册表、预算/权限守卫、领域结果校验和调度提交，不是模型失败后的兜底，也不增加执行模式配置。

## Profile当前声明什么

Profile是代码注册对象，不接受用户/API或模型直接提供。由已核验handoff的domain/intent选择。以下对应当前只读Profile的describe结构：

```yaml
name: mail-calendar-availability-v2
domain: mail
intent: find_free_time_from_mail
goal:
  output_contract: CalendarCandidatesV1
  required_evidence: [MailRequirementsV1]
  missing_information: clarify
risk_limit:
  max_effect: read
  external_write: forbidden
  approval_grant: false
available_capabilities:
  - mail.mail_requirements
  - calendar.calendar_candidates
```

没有allowed_workflows、固定顺序或必须执行几步。available_capabilities是逻辑能力范围；实际步骤仍绑定已注册workflow和编译子图。不同workflow可提供同一逻辑能力与同一可信输出契约，Profile不需要列出每个生产者名字。

目标包含最终产物和机器能核验的证据要求。required_evidence必须由目标依赖链提供，不能只在旁边放一个无关结果，也不能把模型自报完成当成证据。自然语言description用于解释目标，不能替代代码验收，更不声称可以通用判断所有自然语言需求是否已经满足。

## 效果上限与授权的区别

| max_effect | 含义 |
| --- | --- |
| read | 只读业务资料，不创建业务草稿或外部写入 |
| internal_draft | 最多保存站内草稿，不写外部系统 |
| approved_external_write | 可包含既有审批流程保护的外部写入，还须external_write=approval_only |

external_write=forbidden会排除所有带外部写入能力的步骤，即使max_effect较高也不能写。approval_grant只能false。注册步骤效果来自代码中的输出契约/风险声明，不接受模型修改。

当前MeetingConfirmationWorkflow包含批准后创建日历，因此其完整能力效果是approved_external_write，不能冒充纯internal_draft步骤用于只起草目标。会议Profile允许的只是走既有人工确认流程，Profile本身不授予审批；用户拒绝则不写入。若以后提供纯草稿目标，需要独立的无外部写入子图与相应输出契约。

风险策略既在模型候选目录中裁剪，又在Registry.validate复查；不能靠猜测高风险workflow名字绕过。Gateway的连接scope、归属/版本、真实审批、Harness预算和幂等规则保持强制。

## 唯一路径与Agent规划如何选择

```text
可信handoff → Profile.goal / risk_limit / available_capabilities
  → 从已注册输出契约反向检查生产者
     ├─ 所需产物均只有一个生产者，且没有可用可选输入
     │    → 代码构造符号引用计划（deterministic）
     └─ 有替代生产者或可用可选证据
          → CooperationPlanner.complete_json提出计划（agent）
  → 相同Schema / 目标 / 风险 / DAG / 额度校验
  → 相同串行调度 → 每步领域复核 → 完成前证据复核 → 汇总
```

cooperation_resolution.py仅在可信目录内递归解析，受步骤/深度限制，无SQL、模型或工具调用。缺失/循环/有选择的结构不被当作唯一路径。代码生成也不是执行授权，仍经Registry.validate；目标或额度不满足时澄清，不能先调用业务工具。

发生LLM网络故障、预算错误、格式反复无效时，不改走确定流程。规划策略在任何规划调用之前决定；所有真实LLM调用及修复继续经过GuardedLLMClient/Harness累计预算。

现有两个生产目标的能力图确实没有选择，因此默认不调用协同规划模型：

| 意图 / Profile | 目标 / 证据 | 当前自然依赖路径 |
| --- | --- | --- |
| arrange_meeting_from_mail / mail-calendar-meeting-v4 | MeetingDraftV1；MailRequirementsV1与CalendarCandidatesV1 | 邮件要求→日历候选→草稿/确认 |
| find_free_time_from_mail / mail-calendar-availability-v2 | CalendarCandidatesV1；MailRequirementsV1 | 邮件要求→日历候选 |

主Agent路由、邮件语义提取、日历事实规划和会议草稿生成仍按原职责使用LLM。本次省掉的是没有决策价值的协同计划模型调用，不是把所有Agent改成关键词规则。

## 可选输入如何放开

CooperationCapability继续声明必需input_contracts，另可声明optional_input_contracts：

- 必需输入必须准确出现；可选输入可省略，也可选择已注册生产者返回的证据。
- 一旦选择可选证据，必须显式引用其步骤输出并声明依赖；未声明输入类型、伪造引用、重复类型或无关查询仍拒绝。
- 所有计划节点仍须贡献于目标，目标的required_evidence不能被可选字段替代或删除。
- 注册替代生产者不会自动扩大任务权限；同阶段在单个计划仍只允许一次，避免结果键覆盖。

离线测试实际装配替代候选子图，验证同一个Profile无需列举新workflow便可由LLM选择；另一组测试把会议产物对邮件事实的直接引用声明为可选，事实仍经候选步骤传递，验证两种合法依赖形状均能执行并恢复拒绝审批。这些是机制验收，不是假称新增了生产历史邮件/知识检索功能。

## 目标达成由谁判断

计划校验时，目标产物必须唯一存在，必需证据必须是其依赖祖先，风险不得超出上限。完成前，Scheduler逐个重新验证所有实际结果的Schema、状态和领域复核器：邮件来源、候选快照、草稿/审批/版本等。

通过后才产生completed汇总，附goal_output和goal_checks安全引用。缺结果、伪造进度、撤权、候选变化或审批不实，不能先发布completed再报错。结果检查失败不会触发重新规划或重发写入；已批准写入后的其他失败需核对实际执行登记，不能重启任务冒充未执行。

required_evidence是代码可验证的证据类型，不是“模型声称已考虑上次沟通”。未来新增历史/制度业务必须有实际来源、权限、版本及专用结果校验器；不能只在Prompt里添加一句要求就宣布目标可验证。

## 本次未开放的范围

- 生产仍只有既有邮件会议要求、日历候选、会议确认三个步骤；没有注册任意联网、邮件发送、历史沟通、制度检索或新的邮件回复协同。
- “续约回复结合历史沟通和下周可用时间”的Profile是下一类业务的设计样例，不是当前已上线功能。既有MailCollectionWorkflow仍按原邮件起草入口运行，不自动成为协同步骤。
- 缺信息策略目前只支持clarify，不支持Profile声明user.ask后自动获得用户输入工具；通用补问恢复/动态重规划/多专家循环未新增。
- 仍在执行前确定有界DAG，运行中不会让LLM任意改变计划。并行、同阶段多次执行、无限循环仍不支持。
- 新能力须注册真实子图、输入输出Schema、领域校验、风险效果及工具权限；仅新增目录或逻辑名字不会获得执行能力。
