# 8.1 固定跨领域链路：邮件时间要求 → 日历候选 → 会议草稿

## 实现范围

固定子图已实现，默认关闭。只支持一个conversation任务内的固定邮件/日历交接，不引入CooperationPlan、动态DAG、并行、递归子任务或新的Redis任务类型。

首版场景：用户要求“请按续约邮件中的时间要求查询日历并安排会议草稿”。邮件原文例如：

> 请在2026-10-26 09:00 至2026-10-26 17:00之间安排50分钟会议。

邮件中的日期和钟点表示搜索窗口，不是会议本身持续8小时；实际会议仍为50分钟。日历只证明当前用户的可用情况，不证明客户或所有参会人空闲。第三方邮件不是用户承诺或创建批准。

首版仅接受北京时间、绝对日期（YYYY-MM-DD或年月日）、唯一两个钟点、明确阿拉伯数字分钟时长。相对日期、多窗口、时区偏移、缺失时长、用户另提日期/钟点/改期/小时要求或时长冲突均保守澄清；不静默覆盖邮件窗口或用户要求。复杂条件留后续独立扩展，不宣称首版可处理所有邮件会议安排。

## 调用与图结构

```text
TaskGraph（同一run_id / thread_id）
  main_decision
    → mail.arrange_meeting_from_mail（仅显式开启后注册）
    → mail_calendar_meeting固定协同子图
        find_source_mail
          MailAgent.plan_mail → MailQueryService.query → Gateway/mail.messages.list
        extract_and_handoff
          原邮件归属/版本 → Gateway/mail.messages.get
          MailAgent.extract_meeting_evidence（局部连续摘录）
          CalendarAgent.plan_calendar（受限search_window计划）
          代码核验原文日期、钟点、时长和本轮明确参会人
        calendar_meeting（复用日历确认执行节点，跳过重复规划）
          核验邮件来源及原连接权限
          查询可信空闲候选 → 校验范围/时长 → 候选快照摘要
          CalendarAgent生成候选受限草稿 → 保存站内草稿/审批项
          interrupt等待用户确认
          approved：重新核验邮件 → 仅按用户批准版本写日历
          rejected：记录拒绝，不写日历
```

普通查看邮件/摘要/起草仍走原卡片导航，不自动进入协同。新增能力由注册目录和根图节点共同校验；它不能扩大为邮件发送。卡片指代继续使用受控卡片工具及归属/版本复核，目标ID不能由模型凭空构造。完整主题也可不带target，由查询定位；匹配0封或多封时结束并提示先查询/选择，不默认挑第一封。

## 交接与状态

- TaskStepInput只允许固定step_id与带source_version的邮件引用，不包含任意工具、SQL、tenant/user或workflow字段。
- TaskStepResult只允许固定状态、邮件引用/内容摘要、受校验CalendarDecision、候选ID/快照版本、草稿ID及审批ID；不携带邮件原文、模型思维过程或任意输出字典。
- `cooperation_results`按mail_requirements/calendar_candidates/meeting_draft隔离，避免通用plan/tool_result互相覆盖。既有calendar_decision/availability仍是日历子图的工作状态。
- 邮件正文和连续摘录只在extract_and_handoff节点局部使用；日期、时长等核验通过后才形成跨节点结果。摘录必须来自当前原邮件，不能用卡片预览冒充证据。提取最多12000字符源文本、1000字符连续摘录，不支持超范围全文理解。
- source_digest是邮件响应内容摘要，用于批准恢复前新读取的相等复核；candidate_version是受限候选快照的SHA256，不冒充提供商的版本/锁或全局日历版本。最多20候选，候选必须在邮件窗口内并容纳要求时长。
- 暂停时子图尚未向父图提交最终输出，状态保存在同一thread_id的嵌套Checkpoint；恢复用原run_id和Command(resume=...)，不是创建新run。
- 保存草稿前重新查来源及Gateway授权；批准恢复前重新读取原邮件并核验版本/摘要，再调用既有create_approved_event。恢复不重新调用LLM、改变草稿内容或自行生成批准。

步骤结果保存到Checkpoint并发布/持久化cooperation_step_completed安全事件；邮件读取的tool_calls只保存ID/版本等安全元数据。模型/工具真实attempt仍由Harness累计审计。原审批页使用既有草稿、审批项及approval_required卡片；本阶段不新增Artifact类型或协同可视化页面。

## 治理与启用

Worker配置新增`FIXED_COOPERATION_ENABLED=false`。设置true并重启Worker后注册固定协同能力；API无需新路由或新run_type，沿用现有发送对话消息接口。未开启时不能执行该协同能力。

策略不改写已发布v1/v2：

- 无知识查询时，新任务使用harness-v3-fixed-cooperation。
- 同时启用知识查询时，使用harness-v3-cooperation-knowledge。
- conversation工具范围只比原版本增加mail.messages.get；仍禁止mail.messages.send。总工具预算8次（包括卡片、查询、恢复读取和写入）、模型预算10次，其他字符/超时/活跃时长不变。格式修复与网络重试仍累计占用预算，耗尽即停止，不自动扩容。
- Worker保留旧策略注册，旧任务按原持久化策略/余额恢复，不提权、不重置；旧策略任务不能因升级获得邮件正文读取权限。
- cooperation_mail_evidence是独立模型用途标识，不注入个性化记忆；邮件事实规划和日期核验也不注入自由偏好。草稿生成沿用7.4日历用途的受限结构偏好，不能改变可信候选或批准版本。

无新增数据库迁移；需先具备现有020表结构、Checkpoint、Redis、模型、Email MCP和Calendar MCP，以及本人有效mail.read、calendar.read和最终写入所需calendar.write连接。未满足时明确不可用，不伪造会议草稿或外部成功。

不要在仍有协同等待确认任务时关闭开关/移除子图，否则旧Checkpoint无法找到对应节点。先处理或终止这些任务再关闭；保留原策略版本直至存量任务结束。开启不会自动迁移业务库、修改.env或重启服务。
