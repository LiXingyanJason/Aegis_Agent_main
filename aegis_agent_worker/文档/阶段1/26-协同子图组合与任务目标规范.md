# 协同子图组合与任务目标规范（阶段8.3B）

**后续覆盖：** 当前8.3D已移除Profile.allowed_workflows，改为目标/证据、效果上限与逻辑能力；唯一路径不再调用规划LLM。以下“每次模型规划”及v3说明保留为历史。当前实现与部署以[目标风险与混合编排](28-目标风险约束与混合协同编排.md)为准。

## 本次改变

旧实现虽然由LLM输出计划，但注册表要求workflow顺序等于完整MEETING_STEPS元组。本次删除该比较，改为“可信任务目标＋步骤输入输出契约＋有界DAG校验”。仍只有一套受限规划和串行调度器，不重新引入固定执行分支。

```text
MainAgent → 已核验handoff
  → mail_calendar_meeting（保留公开工作流名，两种目标共用）
     → 代码按domain/intent选CooperationProfile
     → LLM从目标允许目录中选步骤，输出依赖及输入引用
     → 注册表验证任务范围、目标、契约、DAG及额度
     → choose_next → 已编译步骤子图 → 业务结果复核 → 提交
     → 继续调度 / 汇总
```

任务Profile不列出完整执行顺序，只列允许步骤及目标产物。计划的顺序由输入输出和依赖决定。会议任务仍自然需要全部三个现有步骤，这是业务必要依赖，不代表允许LLM任意省略安全环节。

## 已开放目标

| 已核验意图 | Profile | 目标产物 | 当前必要步骤 |
| --- | --- | --- | --- |
| mail.arrange_meeting_from_mail | mail-calendar-meeting-v3 | MeetingDraftV1 | 邮件会议要求→日历候选→草稿/确认 |
| mail.find_free_time_from_mail | mail-calendar-availability-v1 | CalendarCandidatesV1 | 邮件会议要求→日历候选 |

两者均须启用COOPERATION_ENABLED。只查邮件仍使用query_mail；精确邮件对象或有效卡片引用规则不变。主题匹配多封时仍要求明确选择，不猜邮箱对象。

测试输入示例（前提：Mock中有唯一匹配邮件且含可核验日期、窗口及分钟时长）：

- “请按《协同测试A｜星河续约会议》邮件的时间要求安排会议草稿。”
- “请按《协同测试A｜星河续约会议》邮件的时间要求只查询我的空闲候选，不生成草稿。”

只读结果是候选窗口，不是确定的会议时间；不表示其他参会人空闲，不产生审批/草稿/日历写入。当前邮件时间要求提取仍限定可核验的北京时间绝对窗口，不因本次组合扩展而支持猜测相对日期。

## 代码守卫

1. Profile只由已核验交接选择；Registry.validate必须显式接收domain/intent，没有默认会议目标。模型计划没有Profile、用户身份、SQL、审批或工具参数字段。
2. 目录是硬白名单；只读Profile不能装配需审批的步骤。主Agent不能凭新意图绕过已注册候选校验。
3. 输入契约必须匹配实际依赖的输出，depends_on必须与引用一致；任务入口允许引用user_request/verified_target，有已核验目标时必须保留该引用。
4. 校验无环、步数、深度、依赖数及字节额度；同一阶段不可重复，避免phase-key结果被覆盖。本版不支持同一类步骤执行多次或并行。
5. 必须恰好一个目标产物生产者，所有节点必须是其依赖祖先；禁止省略目标、夹带无关查询或把会议任务缩为候选任务。这里校验的是图关系，不是workflow完整元组。
6. 输出先受真实Schema验证，再调用代码注册的业务复核器。没有复核器不能启动调度。只有验证后的终态可提交；失败不自动重试、不重发不确定写入。
7. MeetingDraftV1仍强制输入MailRequirementsV1与CalendarCandidatesV1，正式写入仍只使用用户批准版本。Profile.risk不是审批授权，也不会增加Gateway权限或Harness额度。

## 新增业务的方式和边界

1. 定义真实输入输出Schema、稳定阶段和来源规则；当前契约仍显式列举输出类型/阶段，新增类型需同步Schema和进度契约，不能只写字符串冒充注册。
2. 编写有明确输入输出的小子图，工具、身份及预算复用现有治理。
3. 编写结果复核器和必要呈现函数，注册StepResultHandler；声明步骤能力和实际编译对象。
4. 注册任务Profile的允许步骤与目标，在Factory装配。已有意图下新增替代步骤无需改根图；新增主路由意图仍需扩展Intent白名单、候选声明和有关入口规则。这些是显式业务接入，不是改通用调度算法。
5. 补充合法选择、替代生产者、缺前置、越权、失败、审批及恢复测试。扩展目录或改变语义时更新目录/引擎版本并制定在途任务门禁。

本次已注册的生产能力只有上述两种；测试中的替代候选生产者用于证明注册组合机制，不是一个已部署的新业务。知识辅助回复、多专家循环、LLM动态生成节点、自由工具调用及并行调度均未实现。

## 版本与升级

- COOPERATION_ENABLED保持默认false，原三个递进开关仍拒绝使用。
- 目录cooperation-catalog-v3、执行引擎cooperation-scheduler-v3；Profile独立版本见上表。
- Harness仍用harness-v6-cooperation或harness-v6-cooperation-knowledge，集中cooperation-v2配额不变；本次没有预算/数据库迁移。
- v6预算不等于v3引擎：升级前在旧代码结束/拒绝所有在途协同任务并排空队列，尤其v2引擎的待审批任务，不允许混跑或热恢复旧Checkpoint，不修改旧预算余额/版本。此前仅查v3～v5旧预算返回0，不能证明没有v6/v2在途任务。
- 不改真实.env、不操作数据库、不重启服务；回滚同样先处理在途任务，不删除历史审批、事件或业务数据。
