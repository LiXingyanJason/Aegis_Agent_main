# Aegis Agent 第二阶段：RAG 切分与多 Agent 执行策略优化开发计划

> 编写日期：2026-11-01。
> 状态：待讨论、待实施。本文建立优化范围、实验与工程落地顺序，具体算法、参数和验收数值在后续讨论及基线测量后确定，不代表已经选型或实现。
> 前置参考：[阶段 1 开发计划](../阶段1/结构化计划与工具结果状态传递开发计划.md)，重点承接阶段 6「Hybrid RAG 与来源引用」及阶段 8「多 Agent 协同」。阶段 1 保留已有工程建设与历史实施说明，本文单独记录第二阶段的优化工作。

## 1. 目标与总体原则

本阶段围绕两条主线推进：

1. **优化 RAG 切分算法**：减少条款、限定条件与例外分离，改善片段定位和证据完整性，在可控索引与上下文成本下提高检索及回答效果。
2. **优化多 Agent 执行策略的智能选择算法**：改善协调者根据任务状态和专家反馈选择下一位专家、下发子目标及结束任务的能力，减少无进展委派和不必要消耗。

两条主线都采用「固定基线 → 定义问题和契约 → 讨论算法 → 隔离实验 → 消融验证 → 工程接入 → 发布回归」的顺序。先定位失败原因，再决定是否增加模型调用、检索结构或训练环节。

共同约束：

- 复用现有 LangGraph、PostgreSQL、Qdrant、Redis、ToolGateway、Harness、审批及事件体系，不因算法优化重复实现模型通信或引入新的同类基础设施。
- 身份、权限、有效版本、敏感信息、预算、超时、人工审批和幂等由代码执行，不能成为模型自行放宽的策略变量。
- 不预设复杂算法一定优于现有方案，不编造准确率或性能收益；实验结果同时包含失败、成本和适用范围。
- 两条主线分别实验；评测协调策略时固定专家与检索配置，评测切块时固定模型和查询配置，避免无法解释收益来源。
- 本阶段默认不修改前端；如涉及接口、来源结构或事件变化，在主后端接口文档**篇末追加**交接说明。
- 本计划不授权真实外部数据发送、收费实验、生产迁移或真实日历写入；实施时另行明确所需范围与授权。

## 2. 当前基线与范围

### 2.1 RAG 基线

当前代码提供：

- 文本／Markdown 资料导入、索引任务和独立 Embedding 治理；
- `paragraph-v1` 确定性切块，默认约 700 字符、重叠 80 字符，尽量在空行处分割，并提取 Markdown 标题；
- PostgreSQL 保存片段正文、原文位置、内容哈希及权限事实，Qdrant 保存向量与必要引用元数据；
- 权限前置的全文与向量召回、RRF 融合、SQL 复核和来源引用；
- 当前证据摘录上限 800 字符、最多 5 条，检索策略默认结果上限 12,000 字节。它们是现有工程边界，不是新算法的最优参数结论。

待验证问题：条款／列表是否被拆断，例外是否漏召回，标题路径是否不足，正确命中后是否仍缺上下文。切块质量与解析质量、召回排序、回答生成分别归因。

### 2.2 多 Agent 基线

当前团队采用反馈式循环：

```text
协调者读取目标与已核验专家结果
  → 生成结构化决定
  → 注册表及代码守卫校验
  → 委派一个专家执行子目标
  → 核验并观察结果
  → 再次协调或结束
```

协调者可选择 `delegate`、`finish`、`finish_unavailable`；专家内部管理工具查询、补问和恢复。现有任务以「根据续约邮件的时间要求查询日历并安排会议草稿」为最小场景，外部写入仍由独立人工确认链路执行。

待验证问题：选择错误专家、委派目标不清、缺少有效反馈、重复无进展委派、提前结束。专家提取错误、工具故障与协调策略错误须分别记录。

## 3. 主线一：RAG 切分与证据上下文优化

### 3.1 固定语料、查询与基线（待实施）

1. 使用虚构制度、合同、项目说明和会议纪要，覆盖长段落、嵌套标题、编号条款、列表、表格、跨段条件／例外、中英混合及跨章节引用。
2. 为每个问题标注正确文档及版本、原文证据范围、必要条件和例外；不以旧 chunk ID 作为唯一正确答案，保证不同切法可公平比较。
3. 冻结语料快照、查询与改写、Embedding 配置、召回与 RRF 参数、回答模型、随机种子（支持时）和预算；区分检索实验与端到端回答实验。
4. 保存当前切块结果、召回轨迹、答案、耗时和用量作为基线，不直接沿用历史小样本指标证明本次优化收益。

**验收：** 数据集可复跑，证据能回到原文定位，基线与实验配置可追溯；训练／开发与最终测试数据分开。

### 3.2 明确切块与扩展契约（待讨论）

1. 明确结构单元、标题路径、条款归属、原文位置、片段 ID、内容哈希和解析版本的契约。
2. 明确超长段落、单句、列表和表格的拆分／组合规则，以及字符和 Token 上限的区别；具体阈值待实验确定。
3. 如引入标题前缀或生成上下文，区分「用于检索的增强文本」与「可引用的原始证据」，不改写原文后复用旧哈希。
4. 明确直接命中与扩展证据的关系、去重、排序、引用及额度规则；相邻或父级内容不能伪造为直接命中的 RRF 排名。

**验收：** 契约能够表达原文连续范围与扩展来源；生成的说明不能冒充业务事实，权限与版本规则不变。

### 3.3 算法讨论与候选实验（算法待定）

优先讨论以下问题，不在本文提前固定实现：

- 是否按条款、段落、标题路径和文档类型进行结构切分；
- 长结构如何细分，重叠如何处理，如何保留条件与例外；
- 是否增加有界相邻块扩展，还是建立父子块关系；
- 如基础结构方法不足，是否再评估上下文增强、语义切块等方案，以及现有 Embedding 接口是否具备所需能力。

每个候选须补充：要解决的失败样例、输入输出、依赖与成本、边界行为、实验变量、回滚方式。研究性方案和准备上线的方案分别标记，不自动把全部候选纳入实现。

**验收：** 经讨论形成算法说明和独立实验组；每项改动有可以被验证或否定的假设。

### 3.4 隔离实现、指标与消融（待实施）

1. 复用现有索引及检索链路，以策略／解析版本隔离候选；不得向现有业务索引混写实验片段。
2. 分别比较「仅切块变化」「仅证据扩展变化」「组合方案」，必要时对大小、重叠和扩展范围做参数实验。
3. 检索统计证据范围召回、必要条件／例外覆盖、排名指标与重复内容；回答统计正确性、完整性、引用准确性及无证据拒答。
4. 同时统计片段数、索引时间、Embedding 用量、存储量、检索平均／P95 耗时、送入模型的上下文量和回答消耗。
5. 不同切法下 Recall@K 仅为一项指标；同时固定交付上下文预算比较，避免以大量增加片段或正文换取表面召回提升。
6. 回归跨租户、撤权、失效、删除、版本冲突、索引重试及结果大小限制；扩展读取同样在 SQL 内执行授权与版本过滤。

**验收：** 报告可重现的质量／成本对比、样本数和失败案例。质量目标与允许成本增幅在基线完成后、最终测试前确定；非法证据交付必须为 0。

### 3.5 索引迁移与发布（待实施）

1. 根据最终方案明确是否新增字段／表、迁移顺序、解析版本与索引策略版本，不将新解析结果当作旧任务的幂等重试。
2. 设计受控重建、完成校验、有效索引切换及回滚；保留历史来源的明确解析与引用关系，不覆盖或静默删除旧证据。
3. 同一文档版本支持多套切块索引时，明确索引代次及查询选择规则；如沿用新版本重建路线，也须先解决与现有文档版本机制的兼容，不能假设当前已支持自动替换。
4. 若修改证据契约，联动更新来源读取、Artifact、API/SSE 及篇末接口交接，不只放宽单个字段长度。

**验收：** 切换与回滚可演练，无混合索引、引用错位或权限回退；部署及重建步骤有文档。

## 4. 主线二：多 Agent 执行策略的智能选择优化

### 4.1 决策快照与端到端基线（待实施）

1. 从虚构任务构造协调者决策快照：任务目标、有效专家结果、未解决项、允许专家及剩余额度；敏感正文不进入评测日志。
2. 标注允许动作集合、禁止动作与可接受子目标，不强制所有任务只有唯一专家顺序。
3. 建立完整任务集：单封／多封邮件、信息不足、用户改条件、无空闲、来源失效、专家不可用、预算耗尽、补问与审批恢复。
4. 固定当前协调策略、领域专家、工具与 Mock 数据、自动补问答案和预算，记录现有成功及失败轨迹。

**验收：** 同时具备单步选择测试和真实子图端到端测试；任务 `completed` 不直接等同业务成功，Mock 与真实供应商结果分开报告。

### 4.2 定义优化对象与反馈契约（待讨论）

1. 明确优化范围：是否委派、选择哪个已注册专家、委派什么子目标、何时结束；是否扩展其他动作另行讨论，不默认开放并行或新增专家。
2. 讨论协调输入是否显式区分已核验事实、待解决项、最近进展、失败类别及有效产物引用，保持上下文有界并防止摘要丢失限制条件。
3. 讨论委派是否增加预期结果、专家返回是否增加结构化进展信号；不要求输出思维过程，不传播专家完整工具历史。
4. 对错误专家、无效重复、提前结束、合理补问、专家失败和工具故障制定可操作的归因标准。

**验收：** 策略输入输出可校验，反馈来自真实结果；审批、授权与事实核验不能被策略预测替代。

### 4.3 算法讨论与候选实验（算法待定）

可讨论方向包括上下文组织、提示词／示例优化、基于执行反馈的离线优化、候选决策比较及其他数据驱动选择方法。是否采用检索、搜索、收益预测、监督学习或强化学习，由后续讨论与资源条件决定，本计划不预先选定。

1. 每个候选说明需要的数据、模型访问方式、训练／推理成本及与现有循环的接入点。
2. 若涉及模型参数训练，先确认可训练模型与部署条件；不能把调用托管 API 或普通反馈循环称为已完成强化学习。
3. 若使用奖励或排序分数，分别定义任务质量、消耗和错误信号；权限、审批、幂等与预算上限继续作为硬约束，不能用其他收益抵消违规。
4. 自动产生的新规则或提示词先形成候选，经审核和独立评测后发布，不直接在线修改生产策略。

**验收：** 形成明确算法说明、可复现基线及实验组；没有数据或环境支持的方向保留研究状态。

### 4.4 配对实验、故障注入与消融（待实施）

1. 单步实验固定状态快照比较决策；端到端实验从相同起点运行，允许后续轨迹自然不同，不强行套用基线的全部工具调用。
2. 固定模型、专家与工具环境，逐项改变策略输入、提示词或算法；同一案例重复运行，避免单次偶然成功。
3. 统计端到端成功率、单步决策合格率、无进展委派率、提前结束率、补问恰当性及恢复成功率。
4. 统计委派／模型／工具次数、Token、平均／P95 耗时、全部任务成本与每成功任务成本；缺失供应商 usage 记录为 unknown，不冒充 0。
5. 故障注入覆盖模型格式错误、网络／工具超时、取消、来源撤权、并发与重复恢复、审批拒绝；写入不确定时不自动重放。
6. 如进行分支或反事实实验，仅在隔离环境运行，不复用真实审批或真实外部写入。
7. 记录样本数、重复轮数、配对胜负及不确定性；语义评分有明确标准，必要时盲审抽检，不能仅依赖模型自评分。

**验收：** 质量与效率改善可解释，安全回归无新增违规。具体成功率、成本和延迟门槛在基线测量后、最终测试前确定。

### 4.5 策略版本、发布与回滚（待实施）

1. 为最终决策策略记录版本、关联模型／提示词／算法配置，并与实验清单对应；复用现有策略管理，明确与 Harness 安全策略版本的关系。
2. 明确新任务采用新策略、旧任务恢复采用何种绑定规则；不默默改变进行中的任务，安全撤销仍须立即生效。
3. 失败时按既有语义补问、停止或明确不可用，不在模型失败后悄悄执行未经验证的固定链路。
4. 如增加审计或事件字段，保持 SSE 兼容，新增数据库字段单独迁移并说明 API／Worker 部署顺序。

**验收：** 可追溯每次决策使用的策略，发布和回滚不重置预算，不改变审批版本或重复执行写入。

## 6. 推进顺序与阶段交付

1. **基线阶段**：分别完成 3.1、4.1，归因当前问题并冻结评测数据。
2. **设计阶段**：完成 3.2／3.3、4.2／4.3 的算法讨论与契约；在对应小节补充选型结论、未采用方案及理由。
3. **实验阶段**：先单主线、单变量，再组合；新增脚本、配置清单和原始结果索引。
4. **工程阶段**：实现通过评测的方案，补齐迁移、恢复、治理和接口交接。
5. **发布阶段**：回归原有入口、验证部署与回滚，输出实验报告和实际验收结论。

每条主线至少交付：设计说明、固定评测集、复跑脚本、配置与版本清单、原始结果、失败归因及实验报告。报告注明数据是否虚构、工具是否 Mock、是否调用真实模型及哪些环节尚未验证。
