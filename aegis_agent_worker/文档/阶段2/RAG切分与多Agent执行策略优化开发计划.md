## 1. 目标与总体原则

本阶段围绕四条主线推进：

1. **优化 RAG 切分算法**：减少条款、限定条件与例外分离，改善片段定位和证据完整性，在可控索引与上下文成本下提高检索及回答效果。
2. **优化多 Agent 执行策略的智能选择算法**：改善协调者根据任务状态和专家反馈选择下一位专家、下发子目标及结束任务的能力，减少无进展委派和不必要消耗。
3. **建设有界 Deep Research**：围绕复杂资料问题拆解子问题、搜集证据、识别缺口与冲突并迭代检索，最终交付可追溯的研究报告。首版限定已授权内部知识库，不默认开放互联网。

4. **优化记忆需求识别与相关性召回**：在代码指定的模型用途内，判断本次任务需要哪些已确认记忆，减少规则漏召回和无关注入；不是新增主路由，也不开放聊天自动写入记忆。

四条主线都采用「固定基线 → 定义问题和契约 → 讨论算法 → 隔离实验 → 消融验证 → 工程接入 → 发布回归」的顺序。先定位失败原因，再决定是否增加模型调用、检索结构或训练环节。Deep Research 的初版设计不依赖前两条优化全部完成，但实验必须固定所用检索与专家版本。

共同约束：

- 复用现有 LangGraph、PostgreSQL、Qdrant、Redis、ToolGateway、Harness、审批及事件体系，不因算法优化重复实现模型通信或引入新的同类基础设施。
- 身份、权限、有效版本、敏感信息、预算、超时、人工审批和幂等由代码执行，不能成为模型自行放宽的策略变量。
- 不预设复杂算法一定优于现有方案，不编造准确率或性能收益；实验结果同时包含失败、成本和适用范围。
- 四条主线分别实验；评测协调策略时固定专家与检索配置，评测切块时固定模型和查询配置，评测研究循环时固定切块与底层检索配置，评测记忆选择时固定记忆快照、调用用途与回答模型，避免无法解释收益来源。
- 本阶段默认不修改前端；如涉及接口、来源结构或事件变化，在主后端接口文档**篇末追加**交接说明。
- 本计划不授权真实外部数据发送、收费实验、生产迁移或真实日历写入；实施时另行明确所需范围与授权。

## 2. 当前基线与范围

### 2.1 RAG 基线

当前代码提供：

- 文本／Markdown 资料导入、索引任务和独立 Embedding 治理；
- `paragraph-v1` 确定性切块，默认约 700 字符、重叠 80 字符，尽量在空行处分割，并提取 Markdown 标题；
- PostgreSQL 保存片段正文、原文位置、内容哈希及权限事实，Qdrant 保存向量与必要引用元数据；
- 权限前置的全文与向量召回、RRF 融合、SQL 复核和来源引用；
- 当前证据摘录上限 800 字符、最多 5 条，检索策略默认结果上限 12,000 字节。它们是现有工程边界，不是新算法的最优参数结论。

待验证问题：条款／列表是否被拆断，例外是否漏召回，标题路径是否不足，正确命中后是否仍缺上下文。切块质量与解析质量、召回排序、回答生成分别归因。

2026-11-02 源码核对：当前找不到合适空行时按字符边界截断，`section` 仅保留最近匹配的 Markdown 标题，并非完整标题路径；切块参数也限制 `size <= 800`。切分、证据摘录与交付预算须联合设计，不能扩大父块后又直接截取前 800 字符。现有 PostgreSQL 全文／确定性词项检索不等于 BM25，实验报告不得混称。

### 2.2 多 Agent 基线

当前团队采用反馈式循环：

```text
协调者读取目标与已核验专家结果
  → 生成结构化决定
  → 注册表及代码守卫校验
  → 委派一个专家执行子目标
  → 核验并观察结果
  → 再次协调或结束
```

协调者可选择 `delegate`、`finish`、`finish_unavailable`；专家内部管理工具查询、补问和恢复。现有任务以「根据续约邮件的时间要求查询日历并安排会议草稿」为最小场景，外部写入仍由独立人工确认链路执行。

待验证问题：选择错误专家、委派目标不清、缺少有效反馈、重复无进展委派、提前结束。专家提取错误、工具故障与协调策略错误须分别记录。

### 3.2 明确切块与扩展契约（契约设计与独立校验已完成，生产接入随3.3／3.5实施）

8. 不能只全局放宽 800 字符／5 条／12,000 字节限制。先定义候选、扩展和最终交付各自额度及兼容方案；必要例外放不下时记录证据不完整并支持补查或保守回答，不静默裁断后给确定结论。

**验收：** 契约能够表达原文连续范围与扩展来源；生成的说明不能冒充业务事实，权限与版本规则不变。

#### 3.3.1 A：结构基础版

1. 识别 Markdown 标题树、编号条款、段落、列表和表格，先确定结构边界，再按额度合并或拆分。
2. 同章节小单元可合并；列表保留引导句关联。超长段落优先按句子，超长表格按行拆分并关联表头；超长单句／单行仍需确定性硬上限和原文定位，不能无限扩块。
3. 超长条款的子块共享条款归属；重叠优先完整句子／结构单元，记录实际原文范围。“但是／除外”等仅为辅助线索，不宣称关键词能识别全部例外，也不自动扩大到跨章节全文。
4. 以“文档标题＋标题路径＋原始片段”作为可选检索增强文本，先不调用 LLM。标题增强与结构切分分别消融，明确增强用于词项索引、向量或两者，避免混淆变量。

**假设与验收：** 相比字符切分，减少条款拆断和章节背景丢失；原文范围、哈希、超长输入和中英混合边界可单测。成本包括重建索引、片段数和增强输入量，不承诺必然提高召回。

#### 3.3.2 B：证据完整版

1. 在固定切分配置上，命中后优先扩展同条款，其次同章节相邻块；扩展数量、范围和累计上下文均有界，不要求每句单独生成向量。
2. SQL 按可信身份、同文档有效版本和索引代次读取；每个扩展块均需授权及交付前复核，不依赖邻接关系推导访问权限。
3. 合并重复原文范围，保留主体、条件和例外的关联；预算不足时保留完整性状态，不能只保留最像问题的主体而隐藏必要限定。
4. 第一版不默认建立所有层级的向量。若相邻扩展持续引入噪声或缺乏条款范围，再实验父子块：小块定位，PostgreSQL 父结构提供有界上下文。该方案另行设计层级关系、迁移及来源读取。

**假设与验收：** 在相同交付预算下改善必要条件／例外覆盖；扩展证据不伪造直接命中排名、不越权、不无限放大上下文。跨章节引用首批纳入失败分析，不默认解决为整章扩展。

#### 3.3.3 C：排序增强版及暂缓方案

C 在固定 A 或 B 上接入专用 Rerank，严格遵循 3.6。A/B/C 是组合候选，不代替单变量实验，也不代表全部默认上线。

| 后续候选 | 启动条件 | 新增成本与边界 |
| --- | --- | --- |
| 父子块／自动合并 | 已准确命中但同条款／相邻扩展仍不足 | 结构关系、父块读取及迁移；父块不自动整章交付 |
| LLM 上下文增强 | 标题路径不足以解决主体省略、指代问题 | 索引时收费调用、外发及生成错误；增强说明不可作为原始证据，单独版本和治理 |
| 语义切分 | 无明显结构的会议纪要等存在主题混杂 | 句子向量、阈值及重建成本；仅按适用文档类型实验，不能假设优于结构切分 |
| Late Chunking | 确认服务或模型支持 Token 表示及分块池化 | 现有返回整段向量的适配不能直接实现；不得将全文向量再拆分冒充此算法，暂缓 |

每个后续候选须给出失败样例、契约、成本、边界、实验变量及回滚方式，通过开发集证据后才进入独立测试。

#### 3.3.4 调查依据

以下仅支持方法设计，不将外部指标当作本项目收益，也不要求直接引入其 SDK：

- [Docling Chunking](https://docling-project.github.io/docling/concepts/chunking/)：结构层次与长度约束分离，参考结构解析和有界拆分。
- [LlamaIndex Sentence Window](https://developers.llamaindex.ai/python/examples/node_postprocessor/metadatareplacementdemo/)：检索粒度与回答上下文分离，参考命中后的窗口扩展。

- [Anthropic Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)：索引时补充片段背景；本项目确定性标题增强不等同于其模型生成上下文方法。
- [Is Semantic Chunking Worth the Computational Cost?](https://arxiv.org/abs/2410.13070)：语义切分的收益与计算成本需实测。
- [Late Chunking](https://arxiv.org/abs/2409.04701)：长上下文编码后、池化前切块，需要相应模型能力。

### 3.4 隔离实现、指标与消融（离线消融已完成，真实链路／答案／安全验收待完成）

1. 复用现有索引及检索链路，以策略／解析版本隔离候选；不得向现有业务索引混写实验片段。
2. 分别比较「仅切块变化」「仅证据扩展变化」「组合方案」，必要时对大小、重叠和扩展范围做参数实验。
3. 检索统计证据范围召回、必要条件／例外覆盖、排名指标与重复内容；回答统计正确性、完整性、引用准确性及无证据拒答。
4. 同时统计片段数、索引时间、Embedding 用量、存储量、检索平均／P95 耗时、送入模型的上下文量和回答消耗。
5. 不同切法下 Recall@K 仅为一项指标；同时固定交付上下文预算比较，避免以大量增加片段或正文换取表面召回提升。
6. 回归跨租户、撤权、失效、删除、版本冲突、索引重试及结果大小限制；扩展读取同样在 SQL 内执行授权与版本过滤。

#### 3.6.1 接入位置与输入输出契约

1. 首批接入位置：权限前置全文／向量召回 → RRF 去重融合 → SQL 复核并读取有限候选 → Rerank → 选中块的有界证据扩展（开启 B 时）→ 范围去重与交付额度控制 → 最终证据复核与回答。候选数须与最终交付条数分开配置，不先裁成最终 top_k 再重排。若实验扩展后重排，须单独固定输入契约并计入外发量，不与该基线混用。
2. 重排只接收本轮问题和经授权的候选摘录，不发送全库、身份凭据、长期记忆或完整 Prompt；明确发送的是现有证据摘录还是有界片段正文，固定该输入契约后再评测。若需读取更多正文，另行增加权限前置读取与输入额度，不能直接放宽交付契约。
3. 用请求内稳定索引映射 chunk ID／版本／哈希，返回值只能选择或重排本批候选，不接受模型新增正文、来源或候选外 ID。校验重复／越界索引、缺失项、非有限分数与响应大小，定义同分时按原 RRF 顺序稳定排序。
4. Rerank 不改变原文、哈希、权限和有效版本；重排后仍沿用调用前及交付前复核。分别记录原始全文／向量排名、RRF 排名和重排分数，不覆盖原排名、不把相关性分当事实正确率，也不直接用任意阈值声称具备拒答能力。

**验收：** 相同候选映射可追溯；非法返回不能产生新证据，撤权资料不因进入过候选集而继续交付。重排不能补救完全未召回的资料或切块缺失的例外。

#### 3.6.2 适配、治理与失败语义

1. 新增独立重排通信适配和输入输出契约，职责上参照现有 Embedding 分层，但不混用向量协议、模型空间或聊天接口；`HybridRetrievalService` 负责调用编排，不嵌入供应商通信代码。无需为此新增知识库 MCP 或替换 PostgreSQL／Qdrant。
2. 纳入现有 Harness 治理体系，设计重排专属用途、持久化额度与逐次审计；配置调用次数、候选数、单条／总输入上限、超时和响应上限。若现有 attempt 类型／表不能表达，单独设计迁移、API／Worker 部署顺序及测试，不借用聊天用途伪报或新增可重置预算账户。
3. 远端重排会外发“问题＋候选原文／摘录”，不同于只外发查询向量输入；使用前明确供应商、地域、数据范围、资料外发许可和实验费用授权。用户有权访问资料不等于允许外发，必须在供应商请求前检查，不能先发送再过滤。
4. 网络失败、格式错误及供应商限流等以稳定错误分类处理，有界重试仍计预算；预算、外发禁止等治理拒绝不得靠重试或切供应商绕过。无候选或开关关闭时零重排请求。
5. 显式策略可允许重排服务失败时保留已核验的原 RRF 顺序，记录 `rerank_applied=false` 及安全原因；严格模式明确不可用，不静默宣称已重排。治理错误不伪装成普通供应商故障；是否可返回不需外发的 RRF 结果须单独定义并审计。
6. 审计保存策略／供应商／模型标识、候选引用、调用状态、耗时和供应商实际 usage，缺失为 unknown，不记录候选全文、完整 Prompt 或凭据，不用字符数冒充 Token。最终模型／接口选择不写死供应商单价。

**验收：** 所有重排请求受预算、超时及外发约束；故障、降级、取消和恢复均有确定行为，不能通过重排新增无界循环或重置任务预算。

#### 3.6.3 独立消融与发布

1. 对同一冻结候选集比较 RRF 与 RRF＋Qwen Rerank，固定语料、切块、查询改写、Embedding、召回参数及回答模型；补充纯向量基线，不能因历史 E04 中纯向量优于 RRF 就忽略该对照。与切块／证据扩展的组合实验放在单项实验之后。
2. 在相同最终条数及上下文预算下比较 MRR、nDCG、证据范围召回、必要条件／例外覆盖、引用支持及回答质量；同时报告新增请求数、输入量、供应商 usage、平均／P95 延迟和失败／降级比例。重排请求传入的候选量也计入成本，不能只统计最终回答上下文。
3. 覆盖中文、编号、邮箱、中英混合、词面相似但语义无关、否定／例外、跨片段问题及无答案。拒答和分数阈值如需引入，须在开发集单独校准，最终测试前冻结；不事后调阈值美化结果。
4. 测试空候选、同分、重复／越界索引、畸形分数、超大请求、网络／超时、预算拒绝、外发禁止及调用期间撤权；保留重排变差和成本增加样例，目标在基线完成后、最终测试前确定。
5. 通过独立评测才考虑默认启用；新策略绑定模型与参数版本，关闭重排可回到原 RRF。仅改变在线排序通常无需重建向量，但如同时改切块／检索增强文本则遵循 3.5，不混为一次隐式索引升级。
6. 如扩展检索诊断、审计或事件契约，保持兼容，在主后端接口文档篇末追加交接；默认不修改前端。本节仅增加计划，不代表已获真实外发、收费实验或生产迁移授权。

开发集可探索 10／20／40 个重排候选，实际不超过授权召回结果、供应商及 Harness 限制；这些是探索点，不是已选默认值。精确命中等低收益场景也须纳入评测，不通过只挑模糊问题夸大收益。实现时核对[官方 Rerank 接口](https://help.aliyun.com/en/model-studio/rerank)的地域、工作空间、输入约束及 usage，不假定 Embedding 端点可直接复用。

**验收：** 报告可复现的净收益、额外成本及适用范围；收益不足时保留可选或不采用，不能以“增加了模型”作为优化完成标准。

### 5.2 研究状态、证据账本与反馈契约

1. 定义受限研究请求、计划、子问题、动作、观察结果、结论和报告契约；名称在设计阶段确定。计划包含目标、范围与待解决项，不接受模型提供的租户、用户或权限范围。
2. 研究状态显式区分待查、部分支持、已支持、冲突、无法确认；保留问题与证据的关联、检索轮次、来源文档／版本／片段／原文位置及内容哈希。模型摘要不是新的原始证据。
3. State／Checkpoint 保留有界摘要与稳定引用，不累积完整 Prompt、全部原文或模型思维过程；正文由 Repository 在可信身份下读取，持久化需求及清理规则单独设计。
4. 允许模型提出继续查询、调整子问题、补问用户或结束的结构化决定；代码验证动作、查询与额度。模型自报置信度或“已覆盖”不能代替来源核验与验收评分。

**验收：** 每个交付结论能追溯到有效证据或明确标记为推断／未知；修订计划不会丢失用户限定条件，也不能扩大授权范围。

### 5.3 有界研究循环与职责分层

```text
核验研究请求 → 拆解子问题
  → 选择待解决项 → 制定查询 → 受控检索 → 复核证据
  → 更新证据账本与缺口／冲突
  → 继续检索／暂停补问／综合报告／明确结束不可用
```

1. 复用现有知识专家的规划、证据回答能力和 `knowledge.search`，在工作流层管理迭代；Service 管检索、证据事实及报告校验，Repository 管 SQL。新模块应按契约、模型适配、图编排、服务分层，不把全部逻辑写入一个文件。
2. 首版串行执行，不要求多专家讨论、并行搜索或新建多个角色；如后续需要委派，复用团队注册、交接和治理边界，避免同时套用两套无界协调循环。
3. 每轮基于真实检索结果判断缺口与冲突，允许补充查询或调整检索表述；不能把反复相同查询当成进展。重复查询、无新增有效证据、轮次耗尽等条件由代码有界终止，保留原因。
4. 检索轮次、子问题数、查询改写数、累计证据／上下文量、报告大小及无进展次数集中到策略中；具体默认值经基线测量确定。所有 LLM、Embedding、工具调用沿用累计 Harness 治理，不新建可重置的独立预算账户。
5. 正常完成、部分完成、缺少信息、来源不可用、预算／超时、用户取消分别定义结果语义；预算耗尽不伪装成充分研究。允许交付已核验的部分结论，但必须明确未完成项与停止原因。
6. 用户补问复用现有暂停／恢复机制；恢复保留原任务和策略绑定、不重置预算、不重新执行已完成步骤。暂停不等于失败，用户补充不等于批准任何写入。

**验收：** 存在真实的“发现缺口 → 再检索”样例，也能在信息充分时及时结束；循环、恢复和取消均有确定行为，不能靠增加轮次掩盖失败。

### 5.4 来源约束报告、权限与可视交接

1. 报告包含研究范围、主要结论、逐项引用、冲突依据、未知项与局限；区分原文事实和综合推断，不把检索分数、来源数量或模型确信程度称为事实正确率。
2. 每次检索及扩展读取沿用权限前置，已有证据在后续使用及最终交付前重新核验归属、可见性、状态、版本与哈希；撤权后不盲用 Checkpoint 中旧摘录。受影响的中间摘要及结论须失效并重新生成或明确不可用。
3. 资料正文、检索结果及来源中的指令只作为不可信数据，不得改变工具权限或研究范围；冲突无法解决时呈现差异，不编造统一结论。
4. 复用 Artifact 与来源读取服务，按需扩展来源契约，支持多轮证据去重及报告级编号映射；不能假设当前单次结果的最多 5 条／800 字符限制天然适配整份报告，也不能直接全局放宽，须设计独立报告额度与兼容规则。
5. 在现有事件体系上设计计划建立、子问题进展、证据更新、暂停、综合与终止等安全事件，只展示动作、简短进展和引用，不展示思维过程、完整工具正文或 Prompt。新增字段／事件、历史查询与断线恢复的前端交接均在接口文档篇末追加，本轮默认不实现前端。

**验收：** 来源编号准确且可读取；撤权／删除后不交付旧证据，非法证据交付为 0；报告和事件不会因任务状态为 completed 就宣称所有问题均已解决。

### 5.5 隔离评测、发布与后续扩展

1. 固定语料、切块、Embedding、检索策略和模型，对比单次 RAG、固定多查询与动态研究循环；增加不做缺口反馈等消融，区分收益来自更多调用还是研究策略。
2. 同时按相同资源上限和实际消耗报告结果；统计子问题及必要证据覆盖、结论正确／完整性、引用支持率、冲突处理、无证据拒答、无进展率、模型／工具次数、Token 与平均／P95 耗时。引用存在不代表引用支持结论。
3. 多次配对运行，保留失败与提前结束样例；按明确标准逐例评审，必要时盲审，不只依赖模型自评分。成功率及成本门槛在基线后、最终测试前冻结。
4. 故障测试覆盖模型格式错误、检索失败、来源变更／撤权、提示注入、预算耗尽、重复恢复及取消；测试数据和索引隔离，付费与外发实验另行授权。
5. 新能力注册、策略版本、存储／迁移、API／Worker 部署及回滚单独交付；新任务选新策略，旧任务恢复不静默切换，不重置预算。达到验收前不得以现有 RAG 或邮件日历协作代称已完成 Deep Research。
6. 联网研究、网页抓取、跨邮箱／日历研究和并行多专家为后续可选范围，不属于首版承诺。扩展时另行设计 URL／SSRF 防护、来源可信度、内容及下载大小限制、凭据隔离和外发许可，不接受模型直接访问任意网络地址。

**验收：** 有可复跑的数据、配置、轨迹、质量／成本报告和部署回滚说明；确认适用范围后再发布，结果不支持时保留普通 RAG，不强制上线复杂循环。

## 6. 主线四：记忆需求识别与相关性召回优化（待讨论、待实施）

> 2026-11-01 补充。这里的“识别”是判定允许用途内的记忆需求和相关性，不是识别业务路由意图、自动写入意图或权限。是否采用 LLM／Embedding 待评测决定，不因术语为“意图识别”就额外增加一次模型调用。

### 6.1 固定现有边界、数据与基线

1. 当前长期记忆仅由用户页面主动创建、编辑、确认；普通聊天“记住……”不自动创建候选或写库。本主线不改变该边界，若未来支持对话维护须另立计划和确认协议。
2. 调用用途由可信代码指定：普通回复、邮件起草／修改可按需读取；日历规划只接收结构化时区，会议草稿／推荐只接收允许的时区及会议偏好。主路由、事实提取、知识证据回答和审批继续禁止个性化记忆，研究循环不因本优化自动获得记忆权限。
3. 当前 `MemoryContextService` 采用权限前置候选查询及确定性规则：中文双字词项、英文／数字词项、领域信号与实体 key；联系人要求任务显式匹配姓名／邮箱，实体优先、冲突摘要保守排除、去重后限额。没有独立 LLM 意图分类器或语义向量召回，不将现有相关性规则称为语义理解模型。
4. 用虚构用户和已确认记忆构建任务集，覆盖同义／口语表达、无关偏好、短指代、本轮要求覆盖旧偏好、同主题冲突、联系人歧义及显式时区。标注允许用途、可用记忆集合、应排除项和理由；按用户／偏好模板划分开发与测试，避免近重复泄漏。
5. 冻结记忆版本快照、任务文本、用途、候选和额度策略，保存当前召回、选择及无记忆输出基线；将权限过滤、候选漏召回、排序错误、冲突处理与回答未遵循偏好分别归因。

**验收：** 可以独立测量记忆是否相关，而不是只检查答案中出现了偏好关键词；未确认、敏感、过期或来源撤权的记录不得进入模型输入。

### 6.2 明确需求识别与候选选择契约

1. 明确输入为代码给定的 purpose、有界任务上下文和授权候选；输出为允许的偏好类别、候选 ID／版本、稳定原因或“不需要记忆”。未知类别和候选外 ID 拒绝，不能让模型自行扩大用途、实体 key 或权限。
2. 先讨论是否需要独立需求识别步骤，还是改进现有查询提示与排序即可；不要同时新增多个职责重叠的分类器、召回器和选择器。
3. 本轮明确要求优先。未给时区时可使用有效默认时区，已明确时区时不能被历史设置覆盖；偏好不能证明日期空闲、业务价格、公司制度或用户已批准操作。
4. 如引入学习式选择，区分确定性安全检查与语义排序；租户、用户、敏感性、确认状态、有效期、覆盖关系和来源状态仍由 SQL／代码复核。联系人匹配等既有保守规则不随算法替换默认放宽。

**验收：** “没有相关记忆”是正常输出；选择分数、模型置信度和向量相似度不成为授权证明或自动写库依据。

### 6.3 候选算法与治理（算法待定）

1. 先评估低成本规则改进，例如词项归一、同义表达、字段权重与任务信号；每个方案对应已发现的失败样例，不用领域关键词重新决定业务路由。
2. 仅在规则基线不足时，分别实验 Embedding 召回、语义重排或受限 LLM 需求／候选选择；比较纯规则、单项增强与组合，不预设向量或模型方案一定更好。
3. 向量方案复用现有 Embedding 治理和 Qdrant，不以 pgvector 为前置条件；新增记忆索引须设计隔离、更新／删除及撤权行为。向量过滤权限前置，缓存／向量候选回 PostgreSQL 复核后才可读取正文，payload 不是授权事实。
4. 如使用 LLM，使用独立用途及受限 Schema，经 GuardedLLMClient／Harness 累计预算、超时和审计；选择调用不递归加载长期记忆或 Skill。允许发送的候选摘录和任务文本须先核验并限额，不能把全库正文交给模型挑选。
5. 候选数、选择条数、字符／Token额度、额外调用次数、超时及失败策略集中配置。算法不可用时采用明确的规则降级或无记忆；预算耗尽不通过降级绕过治理，不依赖记忆才能回答的场景应明确提示限制。

**验收：** 无候选、无需求时不产生无必要模型调用；新增召回索引、供应商外发与迁移分别说明并授权，不重复实现通信或执行预算。

### 6.4 配对评测、发布与撤销回归

1. 固定任务／记忆快照、调用用途和回答模型，对比不注入、当前规则与候选算法；分别测选择质量和实际回答个性化效果，不能只用终端回答好坏推断召回正确。
2. 统计相关记忆召回率、选择精确率、无关注入率、无需记忆时的误加载率、明确要求覆盖正确率、冲突处理及额外调用／Token／平均和 P95 耗时。无相关记忆任务单独计分，不能排除以提高召回指标。
3. 对回答进行事实保留、偏好遵循和不当承诺核对，保留负面样例；报告样本量、重复次数和不确定性，质量与成本门槛在开发集测量后、最终测试前确定。
4. 回归跨租户／同租户其他用户、删除／停用、过期、覆盖旧值、来源撤权、缓存滞后、向量残留及任务恢复。每次实际调用前重新复核，不能盲用旧 Checkpoint 摘录；不允许用途的调用注入数及非法正文外发必须为 0。
5. 沿用 `MemoryContextBundle`、选择报告和逐 attempt 用量关联，扩展字段需兼容及独立迁移；策略版本、旧任务恢复、缓存失效和回滚规则明确。审计保留 ID、版本及安全原因，不保存完整 Prompt 或敏感正文，Token 缺失为 unknown。
6. 默认不修改记忆管理前端；如增加诊断字段，在主后端接口文档篇末追加。只有离线实验与安全回归通过后才启用新策略，不宣称自动记忆写入或已实现语义召回。

**验收：** 有可复跑的选择与回答对比报告，能够证明收益及成本；撤销及时生效，不放宽既有用途／身份边界，失败时可回到现有规则或无记忆。

## 8. 推进顺序与阶段交付

1. **基线阶段**：分别完成 3.1、4.1、5.1、6.1，归因当前问题并冻结评测数据；研究基线可复用冻结语料，但应有独立复杂问题集；记忆采用独立任务／用户快照评测。
2. **设计阶段**：完成 3.2／3.3、4.2／4.3 的算法讨论与契约，以及 5.2—5.4 的研究契约、循环和交接设计、6.2／6.3 的记忆需求与召回设计；在对应小节补充选型结论、未采用方案及理由。
3. **实验阶段**：先单主线、单变量，再组合；新增脚本、配置清单和原始结果索引。
4. **工程阶段**：实现通过评测的方案，补齐迁移、恢复、治理和接口交接。
5. **发布阶段**：回归原有入口、验证部署与回滚，输出实验报告和实际验收结论。

主线一具体顺序（2026-11-02）：3.1 原文证据标注与基线 → 3.2 契约 → 3.3 A/B 的单项实现与 3.4 消融 → A/B 组合验证。3.6 的适配及治理设计可独立推进，在冻结候选集上进行 Rerank 对照，再验证 C 组合；通过评测的方案最终按 3.5 发布。暂缓候选不得成为首批交付前置条件。

每条主线至少交付：设计说明、固定评测集、复跑脚本、配置与版本清单、原始结果、失败归因及实验报告。报告注明数据是否虚构、工具是否 Mock、是否调用真实模型及哪些环节尚未验证。
