# 记忆边界与结构化契约（阶段7.1）

## 1. 范围

本阶段实现数据契约、纯校验函数与测试，不自动提取/保存记忆，不增加Redis缓存，不修改数据库或接口。
现有`MemoryContextService → SelectedMemory → 格式化字符串`及`run_memory_usages`写入保持不变。
新契约尚未接入实际Prompt，不能将本阶段完成解释为逐次调用审计、删除后恢复复核已上线；这些在7.3～7.5完成。

| 层次 | 用途 | 不做什么 |
| --- | --- | --- |
| working | 当前会话的任务事实、安全摘要、稳定卡片/任务引用 | 不跨会话成为用户偏好，不替代原消息/Artifact/Checkpoint |
| long_term_summary | 经用户确认的稳定跨会话事实摘要 | 不自动复制整段聊天、邮件正文、日程事件、知识库原文 |
| entity | 有明确字段的时区、常用联系人、邮件语气 | 不把联系人当发送批准，不把偏好当工具权限 |

用户当前明确要求 > 已确认且有效的偏好 > 历史摘要。业务授权、审批、连接scope与对象归属始终由代码决定。
摘要来自业务内容时只保留经确认的稳定事实和来源引用，原文继续由业务源管理。

## 2. 文件与职责

| 文件 | 职责 |

| `agent/contracts/memory.py` | 五类结构化契约及实体/来源子Schema，禁止额外字段 |

Service不调用LLM、不执行SQL、不连接Redis。阶段7.3改由用户在长期记忆页面主动录入和确认；本阶段不规划Agent/Workflow自动提取候选，Repository仍负责查询当前事实。

## 3. 五类契约

- `MemoryCandidate`：稳定ID、tenant/user、层次、来源ID/版本、敏感级别、创建/失效时间、适用用途、内容和可选实体；固定pending。
- `MemoryRecord`：候选的事实读取契约，增加版本、更新时间、确认时间与pending/confirmed/revoked/superseded/deleted状态；不是现有表的ORM映射。
- `MemoryContextItem`：可供上下文使用的摘录、记忆ID/版本/类型、身份、来源引用与稳定选择原因。
- `MemoryContextBundle`：一次用途下的有界上下文，绑定run/会话/tenant/user/策略版本；Token估计未知为null。
- `MemoryUsage`：绑定实际模型attempt的使用记录，包含记忆ID/版本/类型、来源、用途、字节数、选择原因，不携带正文或完整Prompt。

身份、敏感分级、确认状态不是模型可自行决定的事实。Schema允许表示这些字段，不等于允许将模型JSON直接当成可信记录。
7.3由主后端校验用户手动录入的身份、来源与状态，用户确认后才能成为有效长期记录。`MemoryCandidate`仅是待确认数据契约，不代表系统会从主对话自动生成候选。
本阶段不提供自动`confirm()`，也不把候选转换为已确认记录或自动创建Usage。

实体Schema使用`key`区分：

- `timezone`：`value="Asia/Shanghai"`，使用ZoneInfo校验IANA时区。
- `contact`：`name`与单一`email`；仅接受保守ASCII邮箱子集，拒绝换行、显示名和多个地址。
- `reply_style`：`formal/concise/friendly`枚举。

实体进入摘录时只使用已校验的实体字段，说明文字不覆盖真实值。
内容限4000字符，禁止空白及明显的密码/API Key/私钥等秘密标记；该确定性检查不是完备DLP或语义敏感信息检测。
候选中的sensitive内容可被表示供后续人工管理，但不能通过使用边界进入Prompt；高危秘密不属于可保存类别。

## 4. 使用边界

将来每次模型调用前，Service从数据库读取记录和当前可访问来源快照，再调用`validate_memory_bundle`：

1. 复核tenant/user、run、conversation、用途与策略版本。
2. 按记录排除未确认、敏感、已失效、未来生效、撤销、删除或被覆盖项；工作记忆还需匹配当前会话。
3. `MemorySourceSnapshot`代表当前读者的代码查询结果，不能来自模型或旧Checkpoint；缺失、删除、无权或版本变化时拒绝。
4. 比对上下文摘录和当前记录的类型、版本、来源及内容；旧摘录不能覆盖新记录。当前最小边界不静默截断长记录；超过额度拒绝，后续选择器可少选或不选。
5. 不允许把同一记忆重复注入，事实快照有重复/歧义时拒绝。

默认可个性化用途：普通回复、邮件起草、邮件草稿完善。主路由、邮件事实提取、知识证据回答和审批禁止个性化注入。
这些是新契约的使用边界，7.4再把旧的两处实际注入接过来。

额度由`PolicyProvider.current().memory`提供：最多5条，单条400字符，总计1500字符、6000个UTF-8正文内容字节。
字节额度只计摘录，不冒充完整序列化Prompt或模型总输入预算；外层Harness仍负责完整输入限制。
Token估计默认unknown；若显式设置Token额度但无可信估计，则拒绝，不将字符数当Token。
供应商prompt_tokens归属于整次调用，在Usage中以call_prompt_tokens表示，不能将其归因为单条记忆的精确消耗。

`format_memory_data`只是低优先级JSON数据格式化函数，不承担权限查询。必须先做上述复核，再按7.4统一接入；
它不创建system消息、不执行JSON中的工具名。JSON转义可防止字符串逃逸结构，但不能证明LLM绝不受语义注入影响。
外部执行仍需现有ToolGateway/Harness/审批守卫，不能依赖提示词隔离。

## 5. 调用示例

```text
当前任务：起草邮件，用户要求“这次语气轻松一些”
  → Service读取“邮件偏好正式”记录及当前来源快照
  → 校验确认/敏感/有效期/来源版本/用途/额度
  → MemoryContextBundle（仅安全数据）
  → 用户本次要求优先，模型可使用其他不冲突偏好
  → 实际发起模型调用后，以attempt关联MemoryUsage（7.4接入）
```

这里不会调用发送邮件工具；“记住联系人邮箱”不代表用户批准向该邮箱发信。
若用户删除偏好，后续调用必须重新查库并拒绝旧Checkpoint中的摘录；本阶段用纯快照测试约束该接口，真实恢复链路在7.4实现。
