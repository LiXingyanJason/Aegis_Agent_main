# 会议安排端到端测试方案（Mock 日历）

## 1. 目标与范围

验证“用户请求安排会议 → 查询空闲时间 → 生成草稿 → 逐项确认 → 恢复 LangGraph → 创建日历事件”的完整服务链路。

本方案验证真实的 Aegis API、Redis、PostgreSQL、Agent Worker、LangGraph PostgreSQL Checkpoint 和 Calendar MCP Server 之间的协作；日历 Provider 使用 `Calendar_mcp_server/data/mock_calendar.json`，不访问 Google、Outlook 等真实账户。

## 2. 前置条件

1. PostgreSQL 已完成 Aegis 业务迁移，且当前 Keycloak 用户存在对应本地 `users`、`tenants` 和有效日历 `provider_connections` 数据。
2. Redis 已启动。
3. `Aegis_backend/.env` 与 `aegis_agent_worker/.env` 中的 `DATABASE_URL`、`REDIS_URL`、模型配置一致；Worker 还应配置：

   ```env
   CALENDAR_MCP_URL=http://127.0.0.1:9001/mcp
   APP_TIMEZONE=Asia/Shanghai
   ```

4. 已能通过 Keycloak 登录前端，或准备好可调用 Aegis API 的 access token。
5. 测试前备份 `Calendar_mcp_server/data/mock_calendar.json`，因为批准测试会向其中追加事件。

## 4. 主成功用例：批准并创建会议

### 4.1 创建并提交任务

1. 登录前端，打开任务工作台；新建或选择一个会话。
2. 输入包含明确触发词的测试语句，例如：

   ```text
   请安排会议，明天与 wangmin@example.com 同步 30 分钟
   ```

   当前一期路由以确定性规则识别“安排会议”“创建会议”“约个会”等表达；不要仅输入“帮我处理一下”。
3. 记录前端返回/保存的 `conversation_id`、`run_id`，并保持该 `run_id` 的 SSE 连接。

### 4.2 验证查询、草稿和暂停

预期顺序：

1. Worker 日志显示收到该 `run_id`。
2. SSE 收到 `run_started`、`progress_updated`、`tool_preview`，其中工具为 `calendar.find_free_time`。
3. SSE 收到 `approval_required`，其中包含 `approval_item_id`、`resource_id`、`action=calendar.create_event` 和会议预览。
4. `GET /runs/{run_id}` 显示：

   ```text
   status = waiting_confirmation
   current_stage = 等待用户确认会议安排
   ```
5. 确认页 `GET /approvals?run_id={run_id}&status=pending` 返回一个日历确认项；预览中的时间、主题、参与者与 SSE 一致。

可选 SQL 核验（将 `{run_id}` 替换为实际 UUID）：

```sql
SELECT id, status, current_stage
FROM agent_runs
WHERE id = '{run_id}';

SELECT id, action, status, resource_id, preview_snapshot
FROM approval_items
WHERE run_id = '{run_id}';

SELECT id, status, title, start_at, end_at
FROM calendar_event_drafts
WHERE run_id = '{run_id}';
```

此时 `mock_calendar.json` 不应新增事件。

### 4.3 批准并验证外部写入

1. 在确认页勾选“我已核对”。
2. 点击“批准”。前端会调用：

   ```http
   POST /approvals/{approval_item_id}/decision
   {"decision":"approved"}
   ```

3. 响应应包含：

   ```json
   {"data":{"decision":"approved","approval_status":"approved_executing","execution_scheduled":true}}
   ```

4. Worker 日志应再次收到相同 `run_id`，并完成恢复后的执行。
5. SSE 应依次出现创建事件相关的 `progress_updated`、`tool_preview`、`approval_executed`，最终为 `assistant_message_completed` 与 `run_completed`。
6. 在 `mock_calendar.json` 中确认新增一条事件。该事件应有新的 `external_event_id`，主题/起止时间/参与者与确认预览一致。

SQL 核验：

```sql
SELECT status, result_summary
FROM agent_runs
WHERE id = '{run_id}';

SELECT status
FROM approval_items
WHERE id = '{approval_item_id}';

SELECT status, provider_resource_id, idempotency_key, error_code
FROM external_action_executions
WHERE approval_item_id = '{approval_item_id}';

SELECT status
FROM calendar_event_drafts
WHERE run_id = '{run_id}';
```

预期：任务为 `completed`，确认项和草稿均为 `executed`，执行记录为 `succeeded` 且包含 `provider_resource_id`。

### 4.4 幂等与重复确认

对同一个 `approval_item_id` 再次提交批准请求。预期 API 返回 `409 Conflict`，且 `mock_calendar.json` 不再增加事件；`external_action_executions` 仍只有本确认项的第一条执行记录。

## 5. 拒绝分支

新建另一条会议任务，直到得到新的待确认项后：

1. 调用或点击拒绝：

   ```http
   POST /approvals/{approval_item_id}/decision
   {"decision":"rejected","reason":"测试拒绝"}
   ```

2. 预期 Worker 恢复同一 `run_id`，但不调用 `calendar.create_event`。
3. `approval_items.status` 为 `rejected`；任务最终 `completed`；`mock_calendar.json` 的事件数量不变；不存在该确认项的成功 `external_action_executions`。

## 6. 失败分支（可选）

在草稿生成后、批准前停止 Calendar MCP Server，然后批准该项目。

预期：

1. Worker 将工具调用、执行记录和确认项记录为失败；
2. `approval_items.status = failed`；
3. `agent_runs.status = failed`，SSE 收到 `run_failed`；
4. `mock_calendar.json` 不新增事件。

完成后重新启动 Calendar MCP Server。不要通过手工篡改确认项状态重试；后续应实现显式的失败恢复/重试用例。

## 7. 当前限制

- Mock Provider 只计算当前用户日历中的忙闲；参与者邮箱尚不代表已查询对方真实日历。
- 当前会议安排策略固定采用第一个可用时间，尚未提供多候选时间供用户选择。
- 确认页需人工刷新或返回任务页观察最终状态；其“批准仅记录决定”的旧文案及自动状态跟踪仍待完善。
- 该文档是手工端到端方案；后续应把主成功、拒绝、工具失败三条路径自动化为集成测试。
