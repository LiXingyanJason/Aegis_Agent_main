部署及权限说明见[阶段6.2](11-知识库权限与Embedding治理-阶段6.2.md)。真实导入和检索仍未接入。

本实现不恢复Skills，不自动把邮件、日历或长期记忆转成资料。

## 1. 文件与调用关系

```text
agent/contracts/knowledge.py         # 四类核心契约及有界检索结果
agent/specialists/knowledge_agent.py  # plan_query / generate_answer，仅调用LLM
agent/workflows/knowledge/
  factory.py                         # 子图与可选对话能力注册
  query_workflow.py                  # 节点／条件边／引用校验／来源持久化
  state.py                           # 与根图共享的有界字段
service/knowledge/
  knowledge_query_service.py         # knowledge.search 的事务、步骤、调用审计及 SSE 编排
  retrieval_service.py               # 检索策略接口，未配置时拒绝
  evidence_service.py                # 版本／权限事实复核，未配置时拒绝
repository/knowledge_repository.py   # Repository协议，真实SQL后续实现
tool/knowledge/handler.py            # knowledge.search内部工具适配，无额外MCP服务
```

```text
MainDecisionWorkflow → knowledge.query_knowledge → knowledge_query
  → 规划与契约校验
  → ToolInvocation("knowledge.search")
  → KnowledgeQueryService（构造 ToolInvocation、事务／审计／SSE）
  → ToolGateway（参数／只读工具／Harness）
  → Handler → RetrievalService → Repository接口
  → EvidenceService复核
  → KnowledgeAgent依据证据回答
  → 引用校验及再次来源复核
  → ConversationArtifactService持久化knowledge_sources、发布artifacts_ready
```

Agent不调用数据库，Service不生成Prompt，Handler不写检索算法，图节点不写SQL。
日历读取使用 `service/calendar/CalendarToolExecutionService`，只接受两个日历只读工具；
知识检索使用独立 `KnowledgeQueryService.query(run, plan)`，返回 `KnowledgeSearchResult`，
不经过日历文本包装。两者共享 Gateway、Harness、审计表及事件协议，不共享领域业务分支。
长期记忆仍由 `service/memory` 管理，与知识资料检索分离。
根图仍沿用现有注册及条件边，知识子图独立结束，不经普通回复节点再生成一个无来源答案。

## 2. 数据契约

| 契约 | 内容与约束 |
| --- | --- |
| KnowledgeQueryPlan | query≤1000字符，最多2条改写、每条≤500字符；top_k为严格整数1～5；只允许project/policy/contract/minutes分类 |
| RetrievedEvidence | source_no、文档／版本／片段UUID、标题、版本标签、章节、字符区间、≤800字符摘录及内容hash |
| KnowledgeAnswer | ≤4000字符答案、严格引用编号、can_confirm；显示的[n]须与编号集合一致且来自本次核验证据 |
| KnowledgeSourceArtifact | knowledge_sources类型、1～5条已引用证据；转换为既有ConversationArtifact保存 |

未知字段拒绝。计划／工具参数不能携带tenant_id、user_id、ACL或连接凭据；身份来自数据库任务的
`ClaimedRun`并由代码转换为`TenantContext`／`ToolContext`。片段结果不包含ACL、向量或全文。
整体证据和Artifact继续使用现有12KB结构化载荷上限。

引用编号合法只证明来源关联正确，不能证明每句话都被证据支持；语义支持度留待6.7实测。
源文本按不可信资料输入，不能成为工具指令。该图没有开放式工具循环或外部写入路径。

## 3. 安全失败与状态

- 非法交接／计划：检索调用数为0，输出安全提示，不回传原始非法JSON。
- 工具不存在／检索未配置：明确不可用，不调用回答模型，不返回Mock资料。
- 空结果、旧版本、撤权后无有效证据：由代码返回“无法从已授权资料确认”，不让模型自由补答案。
- 伪造引用／回答不合法：不发布来源卡片或未经核验的答案。
- 回答生成期间版本变化或撤权：持久化前再次复核，不用新版本悄悄替换旧来源。
- 网络故障、超时、Harness预算错误不按格式错误重试，由现有任务失败链路收尾。

State中的`knowledge_status`为planned/retrieved/verified/answered/succeeded，或
invalid_plan/unavailable/insufficient_evidence；`knowledge_error_code`用于内部稳定诊断。
普通不可用／无证据可以完成本轮处理，run_completed不等于“成功查到资料”，应结合助手文字及工具结果。

首次JSON及最多一次格式修复均通过既有GuardedLLMClient，次数和用量纳入已有Harness审计。

## 4. 配置与部署

新增Worker配置：

```dotenv
KNOWLEDGE_QUERY_ENABLED=false
```

默认不向主Agent公布知识查询能力。工具边界已注册，但默认RetrievalService和EvidenceService没有Repository。
显式启用只用于检查“未配置”提示，不代表真实知识库已可用；开启开关不会加载虚构测试数据。
知识库表／索引接入后，再由启动组合处注入真实Repository并复用同一契约。

新增策略`harness-v2-knowledge-contract`，仅为conversation增加`knowledge.search`白名单，额度保持不变。
不修改已发布harness-v1；Worker保留两版。启用知识能力后新run使用新版，恢复原run仍使用原版本。
默认关闭时新任务继续harness-v1。其他工具、页面任务和审批权限未扩大。

无新增迁移；既有4.5迁移009仍是当前Worker逐次审计的前提。更新代码后重启Worker即可。
不创建额外MCP进程，不自动联网导入文件，不提供知识库管理API。
