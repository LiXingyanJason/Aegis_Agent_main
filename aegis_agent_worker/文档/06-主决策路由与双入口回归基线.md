## 2. 双入口与恢复

```text
首次普通对话：run_type=conversation
  START → select_run_workflow → load_context → main_decision
    ├─ list_events／find_free_time → calendar_read → generate_reply
    ├─ arrange_meeting → calendar_confirmation → interrupt等待审批
    ├─ query_mail → mail_query（邮件操作卡片）
    ├─ reply → generate_reply
    └─ clarify → 已校验澄清文本

首次页面明确任务：不经过load_context和main_decision
  mail_extraction → mail_extraction
  mail_reply_draft → mail_reply_draft
  mail_send → mail_send_confirmation
  mail_draft_revision → mail_draft_revision

恢复：按run_id加载Checkpoint，直接继续原暂停子图
  审批：Command(resume="approved"／"rejected")
  补充信息：Command(resume={question_id,response})
```

会议审批恢复仍可能保留run_type=conversation；它是Checkpoint恢复，不是一个新的日历run_type。
run_type和身份来自数据库，不允许聊天内容把自己声明为页面任务。
邮件发送确认、AI正文修改等注册图不等于对话公开能力。
当前目录只开放日历3种意图和邮件query_mail；用户在聊天里要求摘要／起草，仍只返回列表或单封卡片。
复合任务由主决策澄清；单次邮件起草内的跨工具信息收集是受限ReAct，不是根图多Agent任务分解。

## 4. 最小真实端到端复测步骤（手工，未自动执行）

准备API、Worker、Calendar／Email MCP、Redis及PostgreSQL，应用既有迁移，准备当前用户连接scope、
有效access token及已知Mock日程／邮件。只使用开发数据，写入必须在页面核对并人工批准。

1. `POST /conversations`后在会话发消息，记录返回run_id；通过`GET /runs/{run_id}`与SSE观察。
2. 普通聊天应有main_decision_completed和助手回复；查询日历／空闲应进入对应读图并展示结果。
3. 分别输入“查看邮件”“查看主题为2026年服务续约确认的邮件”“第一封邮件”：
   应返回列表／单封卡片，不能自动执行摘要或起草；首个查询的卡片顺序应用于后续序号。
4. 在卡片点击摘要／起草，或调用`POST /mail/{email_id}/extraction-requests`、
   `POST /mail/{email_id}/reply-draft-requests`；新的页面run不产生main_decision_completed，
   领域模型仍可以调用LLM，这不等于又调用主分类。
5. 起草要求补充信息时用`GET /runs/{run_id}/input-requests`查问题，通过answers接口提交；
   恢复保持同一run_id，收到的回答不能作为发送批准。
6. 请求安排会议，出现待确认项后通过`POST /approvals/{approval_item_id}/decision`批准或拒绝。
   每个分支用独立任务复测，保持原run_id，恢复后不再产生主分类调用。
7. 编辑草稿调用`POST /mail/drafts/{draft_id}/revision-requests`，确认只修改正文且不自动发送；
   提交发送确认继续走既有独立审批链路。
8. 歧义／多任务表达、无效序号和过期引用应澄清或返回受控失败，不随意使用其他对象。

重复比较主路由审计事件、run状态、Artifact和业务记录；工具结果是否正确仍需与Mock文件核对。
真实模型返回会变化，记录输入、版本、run_id及实际结果，不记录凭据或完整敏感正文。

本阶段没有修改HTTP契约、数据库表、Redis协议或Checkpoint恢复标识，无新增迁移。
